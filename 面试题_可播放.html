    模块一：Java 核心技术

    Q1 【中级】【简历依据：熟练-集合】ArrayList 与 LinkedList 的底层结构与增删查效率差异？什么场景选哪个？

    参考答案：ArrayList 基于动态数组，按下标随机访问 O(1)，中间插入/删除需搬移元素 O(n)，尾部追加均摊 O(1)；LinkedList 基于双向链表，插入删除节点本身 O(1)（但需先遍历定位 O(n)），随机访问 O(n)。实际多数业务用 ArrayList 更优（CPU 缓存友好）；LinkedList 仅在已知节点、频繁头尾操作时占优。

    核心考察点：底层结构理解、时间复杂度意识、工程选型。

    深入追问（完整问答）：

    【Q1 追问 1】ArrayList 的扩容机制具体是怎样的？为什么是 1.5 倍？

    参考答案：首次 add 时若为空表，按默认 DEFAULT_CAPACITY=10 初始化；之后当 size == elementData.length 时触发 grow()，新容量 = old + (old >> 1)，即 1.5 倍（位运算高效且避免 2 倍带来的过大浪费）。扩容会 Arrays.copyOf 拷贝旧数组到新数组，代价 O(n)。若预知数据量，应构造时传 initialCapacity 避免多次扩容。

    【Q1 追问 2】subList 有什么坑？为什么会出现 ConcurrentModificationException？

    参考答案：subList 返回的是原 ArrayList 的视图（View），不复制元素，二者共享底层数组。两个坑：① 对原列表结构性修改（增删）后，再遍历子列表会抛 ConcurrentModificationException（modCount 校验）；② 子列表 set 会改到原列表，序列化/独立使用前应 new ArrayList<>(list.subList(...)) 真正拷贝。

    【Q1 追问 3】为什么 LinkedList 在高频随机访问下性能差？

    参考答案：LinkedList 没有连续内存与下标索引，随机访问 get(i) 必须从表头（或表尾，视 i 靠近哪端）沿指针遍历到第 i 个节点，时间复杂度 O(n)。配合 CPU 缓存不友好（节点散落堆中），在循环里频繁 get 会成平方级开销。这也是为什么绝大多数业务应优先 ArrayList。

    Q2 【中级】【简历依据：熟练-集合】HashMap 在 JDK 8 的底层原理？为什么容量是 2 的幂？负载因子和扩容？

    参考答案：JDK 8 为数组 + 链表 + 红黑树（链表长度 >8 且数组容量 ≥64 转红黑树，<6 退化）。容量取 2 的幂是为了用 (n-1)&hash 代替取模，位运算更快且分布均匀；key 的 hash 做高 16 位异或低 16 位（扰动函数）减少冲突。默认容量 16、负载因子 0.75，元素超 容量×0.75 扩容为 2 倍并 rehash。

    核心考察点：哈希表原理、位运算优化、扩容代价。

    深入追问（完整问答）：

    【Q2 追问 1】为什么 JDK 8 选择"链表长度 >8 才转红黑树"？

    参考答案：基于泊松分布的概率论证——在负载因子 0.75、理想哈希下，单桶链表长度达到 8 的概率约为 6e-8（极小），即正常情况几乎不会触发树化；而一旦触发，说明哈希冲突异常严重（可能是劣质哈希或恶意构造），此时树化把查找从 O(n) 降到 O(log n) 是必要的兜底。阈值 8 与退化阈值 6 之间留了缓冲，避免频繁互转的抖动。

    【Q2 追问 2】ConcurrentHashMap 在 JDK 8 是如何实现的？和 JDK 7 的分段锁有什么不同？

    参考答案：JDK 8 废弃 Segment，改为数组 + 链表/红黑树，并发控制用 CAS + synchronized（只锁桶头节点），粒度从"段"细化到"单个桶"，并发度更高。写时：空桶用 CAS 放头节点，冲突则 synchronized 锁住该桶头再插入/树化；读基本无锁（volatile 变量 + 内存可见性）。size 统计用 baseCount + CounterCell 分段累加。

    Q3 【中级】【通用能力补充】HashMap 线程不安全体现在哪？多线程下该用什么？

    参考答案：JDK 8 下并发 put 可能导致数据覆盖、size 不准，极端情况扩容时链表成环（JDK 7 头插法更明显）。多线程用 ConcurrentHashMap（JDK 8 粒度更细、读无锁），或用 Collections.synchronizedMap、写少读多场景 CopyOnWriteArrayList。

    核心考察点：并发安全认知。

    深入追问（完整问答）：

    【Q3 追问 1】ConcurrentHashMap 的 size() 是怎么统计的？为什么不直接用一个全局计数？

    参考答案：为降低并发竞争，size() 不是实时精确值，而是 baseCount（基础计数，CAS 累加成功时更新）+ CounterCell[]（竞争激烈时分散到各 cell 计数）之和。读时没有锁，可能略滞后但性能极高；高并发写入时不同线程打到不同 CounterCell，避免单一变量成为瓶颈。若需强一致计数，应改用 mappingCount() 或外部统计。

    Q4 【高级】【通用能力补充】线程池的 7 个核心参数如何设置？结合"分布式定时任务/批量消息消费"场景说明。

    参考答案：corePoolSize/maximumPoolSize/keepAliveTime/unit/workQueue/threadFactory/handler。CPU 密集型 ≈ N+1，IO 密集型 ≈ 2N 或更大；队列用有界队列防 OOM；拒绝策略按业务选（重要任务用 CallerRunsPolicy 或落库重试）。XXL-JOB 分片广播 + 线程池可并行处理分片数据；MQ 消费端用独立线程池隔离，避免慢消费阻塞拉取。

    核心考察点：参数含义、按场景调参、与简历中 XXL-JOB/MQ 的关联。

    深入追问（完整问答）：

    【Q4 追问 1】线程池的 CallerRunsPolicy 如何实现背压（限流）效果？

    参考答案：当队列满且线程数达最大时，CallerRunsPolicy 会让提交任务的线程自己执行该任务。这天然形成背压：提交方被拖慢 → 上游生产速率自然下降 → 保护线程池与下游不被压垮。代价是占用调用线程（如 Tomcat 工作线程），因此更适合"可调用的同步提交"场景；纯异步解耦场景更宜用"落库/丢队列+告警"的策略。

    【Q4 追问 2】如何监控线程池的队列堆积与负载？

    参考答案：① 继承 ThreadPoolExecutor，定时采集 getQueue().size()、getActiveCount()、getCompletedTaskCount() 等指标上报监控（Prometheus/Grafana）；② 利用 Spring Boot Actuator 的 ThreadPoolTaskExecutor 指标；③ 对关键池自定义拒绝计数与告警。出现持续堆积时优先排查"慢任务/下游阻塞"，而非盲目调大核心线程数（可能加剧资源争抢）。

    Q5 【高级】【通用能力补充】synchronized 与 ReentrantLock 区别？volatile 为什么不能保证原子性？

    参考答案：synchronized 是 JVM 关键字、自动加解锁、非公平；ReentrantLock 是 API、手动 try/finally、可中断/公平/多条件。二者都保证原子性与可见性。volatile 仅保证可见性与禁止重排，不保证原子性（i++ 是读-改-写三步，线程切换会丢更新），需 AtomicInteger 或锁。

    核心考察点：锁机制、volatile 边界。

    深入追问（完整问答）：

    【Q5 追问 1】synchronized 的锁升级过程是怎样的？

    参考答案：JDK 6 后经历 偏向锁 → 轻量级锁 → 重量级锁 的升级（JDK 15 起偏向锁默认废弃/可禁用）。偏向锁：无竞争时 Mark Word 记录线程 ID，免 CAS；轻量级锁：有竞争时 CAS 自旋尝试获取，避免进内核；自旋失败（竞争激烈）升级为重量级锁，线程挂起进 Monitor 等待队列。升级不可逆，目的是"无竞争快、有竞争稳"。

    【Q5 追问 2】CAS 的 ABA 问题是什么？AtomicStampedReference 如何解决？

    参考答案：ABA 指变量从 A→B→A，CAS 只比对值，会误以为"没变过"而更新成功，在涉及"状态机回退/金额"等场景有风险。AtomicStampedReference（或 AtomicMarkableReference）在每个值上附加一个版本号/戳，CAS 同时比对值与戳，即使值回到 A 但戳已变，更新失败。本质是引入"修改次数"维度消除歧义。

    Q6 【高级】【通用能力补充 / 简历关联：排查线上问题】JVM 内存结构？如何排查 OOM / 频繁 Full GC？

    参考答案：运行时数据区：堆（对象，GC 主战场）、元空间（类信息）、虚拟机栈/本地方法栈、程序计数器。排查链路：jps 定位 pid → jstat -gcutil 看 GC 频率与老年代占用 → jmap -histo:live / jmap -dump 导出堆 → jstack 看线程 → MAT 分析大对象与泄漏链（GC Roots 引用）。常见原因：缓存无上限、流/连接未关闭、大对象、堆过小。

    核心考察点：内存模型、排查工具链、与"线上问题排查"职责的关联。

    深入追问（完整问答）：

    【Q6 追问 1】-XX:+HeapDumpOnOutOfMemoryError 怎么用？有什么注意事项？

    参考答案：加该参数后，JVM 在发生 OOM 时自动生成 java_pid.hprof 堆转储，配合 -XX:HeapDumpPath=/path 指定路径。这是线上排障的必备保命参数——OOM 往往难复现，有 dump 才能事后用 MAT 分析大对象/泄漏链。注意：dump 文件可能很大（≈堆大小），需确保磁盘空间；也可用 -XX:+HeapDumpBeforeFullGC 在 Full GC 前dump，但影响更大。

    【Q6 追问 2】G1 与 ZGC 如何选型？

    参考答案：G1（JDK 9+ 默认）按 Region 分代、可设目标停顿 MaxGCPauseMillis，适合绝大多数服务端、堆几 G 到几十 G；ZGC/Shenandoah 用染色指针+读屏障实现亚毫秒级、与堆大小无关的并发回收，适合超大堆（>32G）与极致低延迟（支付/行情），代价是吞吐略低、CPU 占用高。常规业务选 G1；只有"大堆 + 强延迟敏感"才上 ZGC。

    【Q6 追问 3】元空间（Metaspace）OOM 的常见诱因是什么？

    参考答案：元空间存类元数据，由本地内存分配。常见诱因：① 类加载泄漏——动态代理/CGLIB/热部署反复生成新类且旧 ClassLoader 未回收；② 大量 Groovy/脚本引擎/JSP 动态编译类；③ 反射生成的 LambdaMetafactory 类堆积。排查看 jstat -class 类数量是否持续增长，MAT 看 ClassLoader 引用链。

    Q7 【中级】【简历依据：排查线上问题 / Spring 项目】Java 异常处理最佳实践？Spring 项目如何统一处理异常？

    参考答案：① 区分受检/非受检，业务异常用 RuntimeException 子类；② 早抛晚捕，不在底层吞异常；③ 自定义异常带错误码与上下文；④ Spring 用 @RestControllerAdvice + @ExceptionHandler 统一拦截，返回结构化错误；⑤ 关键路径打日志（含 traceId），不把堆栈直接返前端。

    核心考察点：异常设计、全局异常处理（与其"编写接口文档/排查问题"直接相关）。

    深入追问（完整问答）：

    【Q7 追问 1】@Transactional 默认回滚哪些异常？

    参考答案：默认只回滚未受检异常（RuntimeException 及其子类）和 Error；受检异常（Exception 但不继承 RuntimeException，如 IOException）默认不回滚。若业务需对受检异常也回滚，必须显式声明 @Transactional(rollbackFor = Exception.class)。

    【Q7 追问 2】业务里 catch(Exception) 把异常吞了，事务为什么不会回滚？怎么避免？

    参考答案：Spring 事务靠"代理方法抛出异常"来触发回滚；若在方法内 try-catch 吞掉异常（不重新抛出），代理层收不到异常信号，事务会正常提交，造成"数据已改但本应回滚"的脏数据。避免：① 只在确实需要本地处理的异常处 catch，处理完用 throw 或 TransactionAspectSupport.currentTransactionStatus().setRollbackOnly() 显式标记回滚；② 切勿无脑 catch(Exception) 后静默返回。

    Q8 【中级】【简历依据：熟练-Spring Boot】Spring Boot 自动配置原理？@SpringBootApplication 做了什么？

    参考答案：@SpringBootApplication = @ComponentScan + @EnableAutoConfiguration + @Configuration。EnableAutoConfiguration 通过 AutoConfigurationImportSelector 读取 META-INF/spring.factories（Spring Boot 2.7+/3.x 改为 AutoConfiguration.imports）中注册的自动配置类，每个类用 @ConditionalOnXxx（类路径存在、Bean 缺失、配置开关）按需生效，实现"约定优于配置"。

    核心考察点：自动配置机制、条件注解。

    深入追问（完整问答）：

    【Q8 追问 1】如何排除某个不需要的自动配置类？

    参考答案：在启动类用 @SpringBootApplication(exclude = {DataSourceAutoConfiguration.class})（按类）或 excludeName（按全限定名）；也可在 application.yml 用 spring.autoconfigure.exclude 配置。排除后该自动配置不生效，常用于"引入某 starter 但暂不启用其自动装配"的场景。

    【Q8 追问 2】自动配置类的加载顺序如何控制？

    参考答案：用 @AutoConfigureBefore / @AutoConfigureAfter / @AutoConfigureOrder 指定相对顺序（作用于自动配置阶段，区别于 @Order）。例如让自定义 MyAutoConfig 在 WebMvcAutoConfiguration 之后加载，可 @AutoConfigureAfter(WebMvcAutoConfiguration.class)。这保证条件注解依赖的 Bean 先就绪。

    Q9 【高级】【简历依据：封装 Redis / 日志 Starter】如何封装一个可复用的 Spring Boot Starter（以 Redis / 日志为例）？

    参考答案（参考框架，非候选人实际实现）：① 建 xxx-spring-boot-starter 模块，依赖 spring-boot-autoconfigure；② 写 XXXAutoConfiguration，用 @Configuration + @ConditionalOnClass/@ConditionalOnMissingBean 决定生效；③ 用 @EnableConfigurationProperties 绑定 XXXProperties（前缀如 custom.redis）；④ 在 META-INF/spring.factories（或 imports）注册 AutoConfiguration；⑤ 对外提供 XXXTemplate/XXXAspect（如日志切面统一采集操作日志）；⑥ 使用者引入依赖 + 配 yml 即可，无需 @ComponentScan。要点：避免强制依赖（条件注解）、命名规范、spring-configuration-metadata 提示。

    核心考察点：Starter 封装思想、自动配置三要素、可插拔设计——直接对应简历"封装 Redis／日志 Starter"。

    深入追问（完整问答）：

    【Q9 追问 1】@ConditionalOnMissingBean 在 Starter 封装里有什么意义？

    参考答案：它的语义是"容器中还没有该类型 Bean 时才装配我的默认 Bean"。这让使用者可以在自己的项目里定义同名/同类型 Bean 来覆盖 Starter 的默认实现——实现了"开箱即用 + 可定制"的可插拔设计，是 Starter 良好设计的关键（先给默认，用户可覆盖）。

    【Q9 追问 2】Starter 如何避免与应用已有的配置冲突？

    参考答案：① 用独立前缀（如 custom.redis）绑定 XXXProperties，不占用通用键；② 默认 Bean 加 @ConditionalOnMissingBean，允许用户覆盖；③ 用 @ConditionalOnClass 控制"有依赖才生效"，避免强耦合；④ 通过 spring-configuration-metadata.json 提供配置提示与默认值；⑤ 命名空间隔离，不共用应用可能自定义的 Bean 名。

    【Q9 追问 3】操作日志 Starter 用"注解 + 切面"还是"拦截器"实现？各自优缺点？

    参考答案：注解 + AOP 切面（如 @Log + @Around）更常用：优点是与业务代码解耦（只加注解）、可精确织入指定方法、能拿到返回值/异常；缺点是走代理、同类自调用不生效。拦截器（HandlerInterceptor）仅能拦截 Web 请求、拿不到方法内部细节，适合"只记 HTTP 入口"的粗粒度场景。深层链路（业务方法级）首选切面，并建议配合 MQ 异步落库（见 Q21）。

    Q10 【中级】【简历依据：熟练-SSM / Spring】Spring Bean 生命周期？@Transactional 失效的常见场景？

    参考答案：实例化 → 属性填充(DI) → Aware 回调 → BeanPostProcessor 前置 → InitializingBean/init-method → 后置 → 使用 → DisposableBean/destroy 销毁。@Transactional 失效：① 同类自调用（A 调 B，B 注解不走代理）；② 异常被 catch 吞掉；③ 方法非 public；④ 抛出非回滚异常（默认仅 RuntimeException，受检异常需 rollbackFor）；⑤ 数据库引擎不支持（MyISAM）；⑥ 多数据源未指定事务管理器。

    核心考察点：生命周期、事务陷阱（简历大量 DB 操作，必考）。

    【Q10 追问 1】Spring 如何用三级缓存解决循环依赖？

    参考答案：三级缓存：singletonObjects（成品）、earlySingletonObjects（早期引用）、singletonFactories（ObjectFactory）。创建 A 时先放工厂到三级，填充属性发现依赖 B，B 又依赖 A，此时从三级工厂取 A 的早期引用（可在此生成 AOP 代理）注入 B，B 完成后再回头完成 A。关键在第三级工厂能延迟决定是否生成 AOP 代理，避免无循环也被提前代理。

    【Q10 追问 2】构造器注入为什么解决不了循环依赖？

    参考答案：构造器注入要求实例化阶段就拿到完整参数对象，但此时依赖方尚未创建、三级缓存还没来得及放入工厂（工厂是在实例化之后才注册），Spring 无法凭空造出半成品，于是直接抛 BeanCurrentlyInCreationException。解决方式：改用字段/setter 注入，或用 @Lazy 延迟注入（给代理），或重构消除循环。

    Q11 【中级】【简历依据：Spring Cloud Alibaba - Nacos】Nacos 服务注册发现原理？它为什么既能 CP 又能 AP？

    参考答案：服务启动时向 Nacos 注册元数据，消费者订阅实例列表并本地缓存、定时拉取/推送更新。Nacos 对临时实例用 Distro 协议（AP，高可用优先），对持久实例用 Raft（CP，强一致）。通过 ephemeral 区分。注册发现通常选 AP（可用性优先）。

    核心考察点：注册中心原理、CAP 取舍。

    【Q11 追问 1】Nacos 与 Eureka 的主要区别？

    参考答案：① 一致性：Nacos 临时实例用 Distro（AP），持久实例用 Raft（CP），可 AP/CP 切换；Eureka 纯 AP。② 功能：Nacos 同时是注册中心 + 配置中心，Eureka 仅注册发现。③ 健康检查：Nacos 支持临时实例心跳 + 服务端主动探活，Eureka 仅客户端心跳。④ 生态：Nacos 属 Spring Cloud Alibaba，与 Spring Cloud 集成更紧；Eureka 已停更（Netflix 组件退役）。

    【Q11 追问 2】如何降低服务上下线感知延迟？

    参考答案：① 合理设置心跳/上报间隔（Nacos 临时实例默认 5s 心跳、15s 健康阈值）；② 利用 Nacos 的推送（Push）机制（客户端订阅，服务端变更主动推）；③ 应用优雅下线（shutdown 时主动 deregister）；④ 消费者侧对列表变更做快速刷新而非等下次拉取；⑤ 配合就绪探针，避免"未就绪就被路由"。

    参考答案：可以共用同一 Nacos 集群，但建议逻辑隔离——用 namespace（环境隔离，如 dev/test/prod）和 group（业务分组）区分"配置数据"与"服务注册数据"，避免误操作互相影响。生产上也可物理分离（独立 Nacos 集群分别承载注册与配置），提升可用性与故障隔离。

    【Q13 追问 1】网关（Gateway）与业务服务的鉴权职责如何划分？

    参考答案：网关负责"身份认证"（Authentication）——校验 token 合法性、是否登录、是否过期；业务服务负责"权限校验"（Authorization）——该用户是否有权访问这个资源/执行这个操作。这样网关统一挡掉未登录流量，业务侧专注细粒度权限，职责清晰、避免每个服务重复写登录校验。

    参考答案：Gateway 内置 RequestRateLimiter 过滤器，默认用 Redis + 令牌桶（基于 Lua 脚本原子扣减）。配置 redis-rate-limiter 的 replenishRate（每秒令牌）、burstCapacity（桶容量）、keyResolver（按 IP/用户/接口维度限流）。突发流量用 burstCapacity > replenishRate 允许短时burst；分布式下 Redis 保证集群节点共享限流计数。

    参考答案：Spring MVC 基于 Servlet API，一请求一线程（线程池），请求处理期间线程被占用（含 IO 等待），并发高时线程数成瓶颈。WebFlux 基于 Reactor + Netty，响应式非阻塞，少量事件循环线程即可处理大量并发连接，IO 等待时不占线程，适合高并发、低延迟、IO 密集型网关场景。代价是编程模型（Mono/Flux）学习曲线陡，且内部若有阻塞调用会破坏优势。

    【Q14 追问 1】MyBatis-Plus 分页插件的原理？

    参考答案：PaginationInnerInterceptor 是 InnerInterceptor，在 StatementHandler 执行前拦截，识别 IPage 参数：① 先改写原 SQL 为 SELECT COUNT(*) ... 查总数；② 用 LIMIT offset, size（或数据库方言）改写原 SQL 做分页；③ 把结果填回 IPage。本质是 SQL 拦截改写，因此必须保证该插件在拦截器链中且未与其他改写插件冲突；原生 XML 分页也受它影响（取决于配置）。

    【Q14 追问 2】逻辑删除（@TableLogic）与唯一索引冲突怎么处理？

    参考答案：逻辑删除只是把 deleted 置 1 而非真删，因此 (name, deleted) 这类唯一索引在"删除后重插"时会因旧删除记录仍占唯一键而冲突。处理：① 唯一索引改为含 deleted 字段（但多份删除记录仍可能撞）；② 改用 deleted=0 的业务唯一视图 + 应用层校验；③ 关键场景用"物理删除 + 历史表归档"替代逻辑删除；④ 用 NULL 代表未删除（NULL 不计入唯一），删除时填具体值，规避冲突。

    【Q14 追问 3】QueryWrapper 如何防止 SQL 注入？

    参考答案：MP 的条件构造器对值使用预编译 #{}（MyBatis 占位符），而非字符串拼接，天然防注入。风险点在于：① 用 last("limit ...")、apply("...{0}", param) 时若直接拼字符串会注入——apply 必须用 {0} 占位传参；② 用 inSql/exists 拼接子查询时同样要走参数绑定；③ 禁止把用户输入直接拼进 orderBy/last。核心是"永远用占位符，不拼用户输入"。

    Q15 【中级】【简历依据：熟悉-MySQL / 参与查询优化】索引为什么用 B+ 树？explain 怎么看慢 SQL？

    参考答案：B+ 树非叶只存 key（扇出大、树矮、IO 少），叶子有序且链表相连（范围查询快），查询稳定落到叶子层；Hash 仅等值、不支持范围/排序。看 explain：type（至少 range，避免 ALL）、key（实际索引）、rows（扫描行）、Extra（Using filesort/Using temporary/Using index 覆盖索引需优化）。优化手段：加合适索引、避免 select *、避免索引失效（函数/隐式转换/前导 %like/or 非索引列）、优化 order by/group by。

    【Q15 追问 1】最左前缀原则与联合索引怎么设计？

    参考答案：联合索引 (a,b,c) 相当于排序好的多维键，查询必须从最左列开始连续匹配才能走索引（WHERE a=1 AND b=2 走索引，WHERE b=2 不走）。设计原则：① 把等值查询、区分度高的列放前面；② 范围查询列（>/LIKE）放最后（其后列失效）；③ 覆盖常用 WHERE+ORDER BY+SELECT 组合。结合 explain 验证 key_len 用了几列。

    【Q15 追问 2】Using filesort 怎么消除？

    参考答案：filesort 表示无法利用索引完成排序，需额外排序（内存/磁盘）。消除：① 让 ORDER BY 的列命中索引且顺序与索引一致、方向一致；② 利用覆盖索引（索引含排序与查询列，避免回表再排）；③ 缩小排序数据量（先 LIMIT 或先过滤）；④ 适当增大 sort_buffer_size（治标不治本）。本质：把"排序"转化为"按索引顺序读"。

    【Q15 追问 3】深分页 LIMIT 100000, 10 怎么优化？

    参考答案：原生 LIMIT offset, n 在 offset 很大时仍需扫描并丢弃前 offset 行，极慢。优化：① 延迟关联/游标分页：WHERE id > lastId ORDER BY id LIMIT 10，用索引定位起点，O(常量)；② 覆盖索引先取 id 再 join 回表（SELECT * FROM t JOIN (SELECT id FROM t WHERE ... LIMIT 100000,10) x USING(id)）；③ 业务上限制翻页深度（只许翻前 N 页）或用"上一页最大 id"的游标。

    【Q17 追问 1】验证码的 Redis key 设计如何防碰撞？

    参考答案：key 要带足够区分维度并加随机盐，如 verify:{bizType}:{phone}:{uuid}（uuid 为前端每次请求生成的随机串），保证同一手机号不同业务/不同会话不互相覆盖。避免只用 verify:{phone}（多端/重复请求互相覆盖导致串号）。value 存验证码 + 可带过期时间戳，校验时一并比对。

    【Q17 追问 2】验证码明文存 Redis 是否合规？

    参考答案：手机验证码属敏感信息，明文存储有泄露风险（Redis 被拖库即暴露）。建议：① 存哈希值（如 SHA256(验证码+salt)）而非明文，校验时对用户输入做同样哈希再比对；② 配合 TTL 短过期；③ 不在日志/监控里打印验证码；④ 遵循最小必要与《个人信息保护法》——能不存则不存，必须存则脱敏/加密。

    【Q17 追问 3】高并发下用 INCR 做限频，原子性怎么保证？

    参考答案：INCR 本身在 Redis 单线程模型下是原子操作，配合 EXPIRE 需注意二者非原子——应使用 INCR 后判断若返回 1 则 EXPIRE 设窗口（或用 SET key val NX EX + INCR 组合），更稳妥用 Lua 脚本把"自增+设过期/比对上限"打包成原子执行。计数超限即拒绝发送，达到防刷限频目的。

    【Q18 追问 1】布隆过滤器的误判率与容量如何权衡？

    参考答案：误判率 p 由元素数量 n 与位数组大小 m、哈希函数个数 k 决定：固定 n 时，m 越大误判率越低（约 p ≈ (1-e^{-kn/m})^k）。代价是内存。工程中先定可接受误判率（如 1%）与预估元素量，反推 m 和 k。注意布隆过滤器有误判但无误删——"可能存在"需查库兜底，"一定不存在"才直接挡（呼应 Q39）。

    【Q18 追问 2】"延迟双删"的延迟时间怎么定？

    参考答案：延迟双删 = 更库前删缓存 → 更库 → 延迟一段时间再删缓存，堵住"更新期间并发读回填脏数据"的窗口。延迟时长应略大于"一次读 DB + 写缓存"的业务耗时（如 500ms~1s），过短挡不住并发回填，过长则脏数据暴露窗口变大。更彻底的方案是用 binlog（Canal）异步清缓存（见 Q68），不依赖经验值。

    【Q18 追问 3】缓存与 DB 能做到强一致吗？

    参考答案：不能，缓存与数据库是两套存储，任何"先更后删/先删后更"的顺序在并发下都存在不一致窗口。结论：缓存场景只能做到最终一致（秒级内收敛）。若业务强一致要求（如余额），就不该走缓存，或读时强制读主库。面试中要能明确"一致性等级"而非空谈"一致"。

    【Q19 追问 1】分布式锁误删（非持锁线程释放）怎么防？

    参考答案：value 存唯一标识（如 UUID/线程 ID + 机器标识），释放时用 Lua 脚本先比对 value 是否自己、再删除，保证"只删自己的锁"。若不加这层校验，A 锁过期后 B 拿到锁，A 执行完误删 B 的锁，会导致并发失控。Redisson 的 unlock 内部已用 Lua 做此校验。

    【Q19 追问 2】锁超时但业务还没执行完怎么办？

    参考答案：这就是 Redisson 看门狗（Watchdog）要解决的问题：获取锁后后台定时线程每隔 lockWatchdogTimeout/3（默认 10s/3）续期，只要客户端还持有且未主动释放，锁就不会因超时过期；业务完成显式 unlock 后停止续期。这样避免"业务慢于锁 TTL 导致锁提前释放、引发超卖/重复执行"。

    【Q19 追问 3】RedLock 的争议点是什么？

    参考答案：RedLock 通过在 N 个独立 Redis 主节点多数派加锁来提升可靠性，但饱受质疑（如 Martin Kleppmann 的批评）：① 依赖时钟假设——若某节点发生时钟跳变/GC 停顿过长，可能出现"锁已过期但客户端认为还持有"，导致两个客户端同时持锁；② 需要多个独立 Redis，运维与性能成本上升。实践中多数场景 Redisson 单集群 + 看门狗已够用，金融强一致更宜用 ZK/Etcd（见 Q79）。

    【Q20 追问 1】Spring Cloud Stream 的消费组（consumer group）与分区（partition）是什么？

    【Q22 追问 1】项目同时维护 RabbitMQ 和 RocketMQ，成本如何权衡？会不会是过度设计？

    参考答案：维护两个 MQ 确实增加运维、监控、故障面。合理情形是"按场景分层"：RabbitMQ 做一般业务解耦（协议丰富、易用），RocketMQ 做对一致性/事务/堆积要求高的链路（如订单/金融）。但若两者干的事差不多，就是过度设计——应评估能否收敛到一个（多数业务 RocketMQ 或 RabbitMQ 二选一即可），用"复杂度换必要性"来论证。

    【Q22 追问 2】RocketMQ 如何保证顺序消息？

    参考答案：顺序消息靠相同业务 key 路由到同一 queue + 单队列单线程串行消费。生产者用 MessageQueueSelector 按 orderId 选固定 queue；消费者对该 queue 加锁串行消费。代价是并发度下降。注意：顺序消息消费失败会阻塞该 queue 后续消息（需谨慎设置重试与跳过策略）。

    参考答案：RocketMQ 事务消息先发"半消息"（对消费者不可见），执行本地事务后提交/回滚；若 Broker 长时间未收到确认会回查 checkLocalTransaction。兜底：① 回查时查本地事务状态（DB 订单状态）决定提交/回滚；② 若本地状态也查不到（极端），记入"待人工确认"表定时重试；③ 业务侧最终一致依赖"状态机 + 主动查单/对账"补齐（呼应 Q88）。

    【Q39 追问 1】如果布隆过滤器误判，导致本来该"穿透"的请求被拦截（误判为存在但实际无），业务会怎样？

    A. Java 基础与集合（补充）

    Q40 【中级】【简历依据：熟练-集合/设计模式】equals 与 hashCode 的契约是什么？在简历项目（如订单/用户去重）中什么场景会踩坑？

    参考答案：约定——相等的对象 hashCode 必相等；hashCode 相等对象未必相等。HashMap/HashSet 先比 hash 再比 equals，若只重写其一会导致"相等对象存不同桶"查不到。场景：把订单/用户对象当 Map key 或放入 Set 时，若用默认 hashCode（对象地址）而业务按 ID 判等，去重失效。解决：以业务主键重写两者，或干脆用 ID 而非对象做 key。

    核心考察点：契约理解、集合去重坑。

    深入追问（完整问答）：

    【Q40 追问 1】String 的 hashCode 为什么用 31 这个素数？

    参考答案：公式为 h = 31*h + val[i]，选 31 因为：① 31 是奇素数，能减少哈希冲突（偶数乘 2 的幂易信息丢失，合数增加碰撞）；② 31 的乘法可被 JVM 优化为 i*31 == (i<<5)-i，移位+减法比普通乘法快；③ 经验上分布较均匀。本质是在"冲突率、计算速度、分布质量"间取平衡。

    【Q40 追问 2】两个不同对象 hashCode 相同（哈希碰撞）会怎样？

    参考答案：哈希碰撞后它们被分到 HashMap 同一桶，桶内用链表（或红黑树）存储，查找时需再 equals 逐个比对，性能退化为 O(n)/O(log n)。只要 equals 正确实现，碰撞不影响正确性，只影响效率。因此好的 hashCode 要"尽量分散"，降低碰撞概率与桶内长度。

    Q41 【高级】【简历依据：常用设计模式】你在 Spring/中间件里用到过哪些设计模式？举一个你能说清"为什么这么设计"的例子（如 Starter 封装、MQ 消费）。

    参考答案（参考框架）：Spring 大量用工厂（BeanFactory）、单例（默认 Bean）、模板方法（JdbcTemplate/RestTemplate）、代理（AOP）、观察者（事件 ApplicationEvent）、策略（HandlerMapping）。以简历"封装 Redis/日志 Starter"为例：用模板方法 + 自动配置 + 条件注解把"创建客户端/切面"固定下来，业务只配 yml——这是模板方法（固定流程）与工厂（创建 Bean）的组合，降低复用成本。关键点：说清"问题—模式—收益"，而非背定义。

    核心考察点：模式落地能力、设计取舍（避免"为模式而模式"）。

    深入追问（完整问答）：

    【Q41 追问 1】Redis 客户端（连接/模板）应该用单例还是原型管理？

    参考答案：应单例——Redis 客户端（如 RedisTemplate、Redisson Client）本身线程安全、内部维护连接池，全局一个即可，频繁创建会耗尽连接、浪费资源。原型（每次 new）是错误的。Starter 封装时通常 @Bean 默认单例 + @ConditionalOnMissingBean 允许用户覆盖，并注入连接池配置。

    【Q41 追问 2】为什么日志切面用"责任链/多个通知"比单个 if 更易扩展？

    参考答案：日志采集常涉及"前置取参 → 环绕计时 → 后置存库 → 异常记录"多步，用多个 @Before/@After/@AfterThrowing 或责任链模式，每步独立、可插拔（如新增"脱敏"只需加一个处理器），符合开闭原则。单个 if 堆在一处会膨胀成"上帝方法"，改一处易错、难测试。这是"把变化点拆成独立节点"的设计收益。

    Q42 【高级】【通用能力补充】反射与注解的底层原理？Spring 是如何用它们实现 IOC/AOP 的？

    参考答案：反射（Class/Field/Method）在运行时获取类信息并调用，性能低于直接调用（JVM 有 setAccessible 与 invokedynamic 优化）。注解本质是继承自 Annotation 的接口，编译期写入类文件属性表，运行时 getAnnotation 读取。Spring IOC 用反射创建 Bean、注入属性；AOP 用反射+动态代理在切点织入（JDK 代理基于接口反射，CGLIB 基于 ASM 改字节码）。

    核心考察点：反射/注解机制、与 Spring 的关联。

    深入追问（完整问答）：

    【Q42 追问 1】反射大量调用如何优化？

    参考答案：反射比直接调用慢（有安全检查、动态解析）。优化：① 缓存 Method/Field 对象，不要每次 getDeclaredMethod；② 调用前 setAccessible(true) 关闭访问检查（提升明显）；③ 用 MethodHandle（JDK 7+，更接近直接调用）；④ 热点路径考虑 invokedynamic/字节码生成（如 CGLIB/ASM）；⑤ 或用 Constructor.newInstance 缓存。本质是"减少重复解析 + 关闭检查 + 缓存"。

    【Q42 追问 2】CGLIB 代理类为什么不能被 final 类/方法代理？

    参考答案：CGLIB 通过生成目标类的子类（继承）并在子类中重写方法织入增强。而 final 类不可被继承、final 方法不可被重写，因此 CGLIB 无法代理它们。JDK 动态代理基于接口则不受此限（但要求有接口）。这也是为什么 Spring AOP 对 final 方法会"静默失效"——代理织不进去。

    B. 并发编程（深入）

    Q43 【高级】【通用能力补充】CompletableFuture 如何做异步编排？相比 Future/@Async 强在哪？踩过什么坑？

    参考答案：CompletableFuture 支持 thenApply/thenCompose（依赖）、thenCombine/allOf（聚合）、exceptionally（异常恢复）、自定义线程池。相比 Future 只能阻塞 get、无回调；相比 @Async 更细粒度可控。坑：① 默认用 ForkJoinPool.commonPool()，IO 密集会拖垮全局 → 必须传自定义线程池；② 异常若不 handle 会被吞；③ 不 join/get 任务可能不执行。

    核心考察点：异步编排、线程池意识。

    深入追问（完整问答）：

    【Q43 追问 1】如何限制 CompletableFuture 的并发度？

    参考答案：① 用自定义线程池并把 corePoolSize/maximumPoolSize 设为期望并发数（最直接）；② 或用信号量（Semaphore）在提交任务前 acquire，控制同时运行的任务数；③ 或把大任务分批量、每批 allOf 等上批完成再下批。避免用默认 ForkJoinPool.commonPool()（全局共享、IO 密集会拖垮其他任务）。

    【Q43 追问 2】thenApply 与 thenApplyAsync 的线程差异？

    参考答案：thenApply（无 Async 后缀）默认在上一个阶段所在的线程或调用线程继续执行（同步衔接，无额外线程切换）；thenApplyAsync 会把任务提交到指定的线程池（或默认 ForkJoinPool）异步执行，不阻塞上游线程。需要并行/不阻塞时用 Async 版，并注意传自定义线程池避免踩默认池的坑。

    Q44 【高级】【通用能力补充】ReentrantLock 的底层（AQS）是怎么实现的？和 synchronized 在锁升级后的性能差异？

    参考答案：AQS 用一个 volatile state + CLH 队列，获取锁 CAS 改 state，失败入队 park 挂起；释放时 unpark 后继。ReentrantLock 公平/非公平靠是否先排队。synchronized 在 JVM 内做锁升级（偏向→轻量→重量），低竞争下更轻；高竞争且需公平/中断/多条件时 ReentrantLock 更灵活。JDK 6 后两者性能接近，一般场景首选 synchronized（简单不易错）。

    核心考察点：AQS 原理、锁选型。

    深入追问（完整问答）：

    【Q44 追问 1】AQS 为什么用 volatile state + CAS 而非 synchronized？

    参考答案：AQS 是锁机制的底座，若它自己用 synchronized 就成了"用锁实现锁"，且 synchronized 不提供"尝试获取/超时/可中断"等细粒度控制。AQS 用 volatile state 保证可见性、CAS 保证原子争抢，配合 CLH 队列把竞争线程 park 挂起，实现"无锁争抢 + 队列等待"的高效模型，并能支持公平/非公平、可中断、超时等语义——这是 synchronized 早期（未优化前）不具备的灵活性。

    【Q44 追问 2】CLH 队列如何避免惊群（thundering herd）？

    参考答案：CLH 是单向链表，每个节点只唤醒它的直接后继（unpark next），而非广播唤醒所有等待线程。这样锁释放时只有队首线程被唤醒去抢锁，其余继续 park 等待，避免"一锁释放、全员醒来抢、多数又睡"的惊群浪费。配合 state 的 CAS，保证同一时刻只有一个线程成功获取，队列有序推进。

    Q45 【中级】【通用能力补充】CopyOnWriteArrayList 适用什么场景？为什么不适合写多读少？还有哪些并发容器？

    参考答案：COW 写时复制整个数组，读无锁、写加锁，适合读多写极少（如监听器列表、配置）。写多会频繁复制大数组、内存占用高、数据有短暂不一致。其他：ConcurrentHashMap（分段/CAS）、ConcurrentLinkedQueue（无锁队列）、BlockingQueue 系列（ArrayBlockingQueue/LinkedBlockingQueue，用于线程池/生产者消费者）。

    核心考察点：并发容器选型（济南驻场/后台常考）。

    深入追问（完整问答）：

    【Q45 追问 1】ConcurrentLinkedQueue 的 size() 为什么慢？

    参考答案：它是无锁（CAS）队列，没有维护一个原子计数器。size() 必须遍历整个链表实时统计节点数，O(n) 且并发下结果也只是近似值（遍历途中节点可能变化）。因此高频需要"队列长度"时应另用原子计数器或改 BlockingQueue（其内部常维护 count），别在循环里反复调 size()。

    【Q45 追问 2】ArrayBlockingQueue 与 LinkedBlockingQueue 区别？

    参考答案：① 底层：ArrayBlockingQueue 是有界数组（构造必指定容量），LinkedBlockingQueue 默认无界链表（也可指定容量）；② 锁：Array 用一把锁控制入出，Linked 用两把锁（入队锁/出队锁）并发度更高；③ 内存：数组预分配、链表节点分散。生产环境推荐有界队列（防 OOM），LinkedBlockingQueue 不指定容量有撑爆风险。

    Q46 【进阶】【通用能力补充】如何用 jstack / Arthas 定位死锁与高 CPU 线程？给一个实战步骤。

    参考答案（参考框架）：① top 找高 CPU 进程 pid → top -Hp pid 找线程 tid → printf "%x\n" tid 转十六进制；② jstack pid | grep -A 30 nid=0x.. 看该线程栈；③ 死锁直接看 jstack 输出的 "Found one Java-level deadlock"；④ Arthas：thread、thread -b 一键找阻塞、thread <id> 看指定线程。实战：曾遇线程池任务互相持有锁导致死锁 → 统一加锁顺序 / tryLock(timeout) 解决。

    核心考察点：线上排查工具链（对应简历"排查线上问题"）。

    深入追问（完整问答）：

    【Q46 追问 1】jstack 在容器里怎么拿？

    【Q46 追问 2】native 线程（JNI）CPU 高，jstack 看得到吗？

    参考答案：jstack 只显示 JVM 管理的 Java 线程栈，native（C/C++ 通过 JNI 调用）代码的 CPU 占用不会出现在 jstack 的 Java 栈里——你只能看到 Java 线程"卡在某个 native 方法"，但看不到 native 内部。排查 native 高 CPU 需用 OS 级工具（top -Hp + perf/pstack/async-profiler 的 native 模式），jstack 只能定位到"是哪个 Java 线程调用了 native"。

    Q47 【高级】【简历依据：排查线上问题 / 通用】ThreadLocal 在你们项目（如用户信息传递、TraceId）里怎么用的？线程池下为什么会内存泄漏或串号？怎么防？

    参考答案：用于跨方法透传用户上下文 / 链路 traceId，避免层层传参。坑：① 线程池复用线程，若不清 ThreadLocal，下次任务读到上次的脏数据（串号）；② key 是弱引用、value 强引用，线程不结束则 value 泄漏。防护：用完 remove()（推荐 try-finally）；或改用 TransmittableThreadLocal（阿里，支持线程池上下文传递）做跨线程透传。

    核心考察点：ThreadLocal 实战坑（与简历"排查问题"强相关）。

    深入追问（完整问答）：

    【Q47 追问 1】InheritableThreadLocal 在线程池里为什么不行？

    参考答案：InheritableThreadLocal 只在创建子线程时把父线程的值拷贝给子线程。而线程池的线程是预先创建、被任务复用的，任务提交时并不会"继承"当前线程的 ThreadLocal 值（线程早就在那了），且复用会导致脏数据串号（上一个任务的 value 被下一个任务读到）。所以它解决不了线程池上下文传递。

    【Q47 追问 2】TransmittableThreadLocal（TTL）怎么解决线程池串号？

    参考答案：TTL（阿里开源）通过装饰 Runnable/Callable实现：提交任务时把当前线程的 TTL 值快照存入任务包装器；线程池执行该任务前，把快照设入执行线程的 TTL，执行完再恢复原值。这样即使线程复用，每个任务用的都是"提交时"的上下文，且不会污染其他任务，完美解决线程池/异步场景的上下文传递与串号问题（呼应 Q77 traceId 传递）。

    Q48 【高级】【通用能力补充】JMM（Java 内存模型）解决了什么？volatile 的"可见性+有序性"在硬件层是怎么保证的？

    参考答案：JMM 定义线程与主存的抽象关系，规定 happens-before 规则，屏蔽硬件差异，保证多线程下可见性与有序性。volatile 写后插入写屏障（强制刷新主存、禁止后续重排），读前插入读屏障（强制从主存读、禁止前面重排）；x86 下主要靠 lock 前缀指令（如 lock addl）实现MESI 缓存一致性 + 内存屏障。它不保证原子性。

    核心考察点：内存模型底层（济南高级岗常考）。

    深入追问（完整问答）：

    【Q48 追问 1】happens-before 有哪些主要规则？

    参考答案：核心规则：① 程序次序：单线程内前面的操作 hb 后面的；② volatile 规则：volatile 写 hb 后续的 volatile 读；③ 锁规则：unlock hb 后续的 lock；④ 线程启动：Thread.start() hb 线程内任何操作；⑤ 线程终止：线程内操作 hb 于 join() 返回；⑥ 传递性：A hb B 且 B hb C ⇒ A hb C。这些规则是判断"多线程下某读能否看到某写"的法定依据。

    【Q48 追问 2】DCL（双重检查锁）单例为什么必须 volatile？

    参考答案：DCL 单例 instance = new Singleton() 在底层是三步：① 分配内存；② 初始化对象；③ 把引用指向内存。由于指令重排，可能 ①③②（先指向、未初始化完）。此时另一线程在"第一次检查"看到 instance != null 就直接返回，拿到半初始化对象（字段为默认值），导致诡异 bug。volatile 禁止该重排，保证"引用可见时对象已完全初始化"。

    Q49 【高级】【通用能力补充】G1、ZGC、Shenandoah 的区别与选型？为什么大堆（数十 G）优先 ZGC？

    参考答案：G1 把堆分为 Region，可预测停顿（MaxGCPauseMillis），JDK 9+ 默认，适合多数服务端；ZGC/Shenandoah 用染色指针 + 读屏障做并发整理，停顿亚毫秒级、与堆大小无关，适合超大堆/低延迟（金融交易、实时）。代价：吞吐量略低、CPU 占用高。选型：常规业务 G1；堆 >32G 且对延迟敏感（如支付/行情）用 ZGC。

    核心考察点：收集器演进与权衡。

    深入追问（完整问答）：

    【Q49 追问 1】G1 的 Humongous 大对象分配有什么坑？

    参考答案：G1 中超过 Region 一半（约 -XX:G1HeapRegionSize/2）的对象算"大对象（Humongous）"，直接分配在连续的 Humongous Region，且不进年轻代、Full GC 时才回收。坑：① 大对象多会快速耗尽 Region、触发频繁并发标记/Full GC；② 分配大对象需找连续空间，可能提前触发 GC；③ 复制成本高。建议：避免超大对象、调小 Region 或拆分对象。

    【Q49 追问 2】ZGC 的"染色指针"为什么需要保留几位地址？

    参考答案：ZGC 把对象状态（标记/重定位信息）直接编码进指针的高几位（染色指针），读对象时通过读屏障解读。因此可用地址位数减少——Linux 上 64 位地址实际只用 48 位（x86 规范），ZGC 再借几位（如 42~45 位）存标记，导致可寻址空间受限（如 4TB~16TB 级，对绝大多数服务足够）。这是"用地址位换并发能力"的权衡。

    Q50 【高级】【通用能力补充】双亲委派如何打破？Tomcat、JDBC（SPI）、OSGi 各为什么需要打破？

    参考答案：默认双亲委派保证核心类唯一安全；打破即重写 loadClass 或用自己的类加载器先加载。Tomcat：WebAppClassLoader 先加载本应用类再委派，实现应用间隔离（不同 war 用不同类）；JDBC 4.0 SPI：DriverManager 由启动类加载器加载，却要加载各厂商驱动（应用类加载器），故用线程上下文类加载器逆向委派；OSGi 实现模块级热部署需网状委派。

    核心考察点：类加载机制与真实场景。

    深入追问（完整问答）：

    【Q50 追问 1】同一个类被两个不同类加载器加载，instanceof 成立吗？

    参考答案：不成立。JVM 中类的唯一性由"类加载器 + 全限定类名"共同决定——即使字节码完全相同，不同加载器加载出的 Class 对象也是两个不同的 Class。因此 a instanceof B 会返回 false（或抛 ClassCastException），即使它们"看起来一样"。这正是类加载隔离/冲突的根源。

    【Q50 追问 2】如何排查 ClassCastException: X cannot be cast to X？

    参考答案：这个"自己不能转自己"的诡异报错，典型就是类加载冲突——同名的 X 被两个加载器各加载了一份。排查：① 打印 obj.getClass().getClassLoader() 与 目标 X.class.getClassLoader()，确认是否不同；② 检查是否重复引入 jar、Web 容器与应用各自带了一份；③ 用 -verbose:class 看类从哪加载；④ 统一依赖版本、排除冲突 jar。本质是"让同一份类只被一个合理的加载器加载"。

    Q51 【进阶】【通用能力补充】JVM 内存溢出有哪几类？各自现象、原因与排查手段？

    参考答案（参考框架）：

    堆 OOM（java.lang.OutOfMemoryError: Java heap space）：对象过多/泄漏，MAT 分析大对象；

    元空间 OOM（Metaspace）：类加载泄漏（动态代理/热部署反复生成类）；

    栈溢出（StackOverflowError）：递归过深；

    直接内存 OOM（NIO ByteBuffer.allocateDirect）：-XX:MaxDirectMemorySize 不当；

    GC Overhead Limit：98% 时间 GC 却回收 <2% 内存（基本是泄漏）。

    排查：jstat/jmap/MAT + 对应参数（-XX:+HeapDumpOnOutOfMemoryError）。

    核心考察点：溢出分类与根因（高级岗区分度）。

    【Q51 追问 1】为什么 Spring AOP + 热部署容易元空间 OOM？

    参考答案：Spring AOP/CGLIB 会为被代理的 Bean 动态生成代理类（新 Class），热部署（如 devtools、JRebel、反复 redeploy）每次 reload 又生成一批新代理类，而旧的 ClassLoader 若未被回收，这些类就一直占着元空间，反复累积直到 Metaspace 溢出。排查看类数量持续上涨、ClassLoader 实例堆积；解决：避免开发期频繁热部署、升级时清理旧 ClassLoader、控制代理范围。

    【Q51 追问 2】Netty 直接内存泄漏怎么查？

    参考答案：Netty 用 ByteBuf.allocateDirect（堆外直接内存），泄漏不归 GC 管。排查：① 开启 -Dio.netty.leakDetection.level=PARANOID（开发期），Netty 会在发生泄漏时打印资源泄漏警告与创建栈；② 用 ResourceLeakDetector 报告定位未 release() 的 ByteBuf；③ 监控直接内存用量（-XX:MaxDirectMemorySize + NMT）；④ 确保每次 ByteBuf 用完都 release()（或用 try-finally/ReferenceCountUtil）。

    Q52 【高级】【通用能力补充】对象是怎么在堆里分配与晋升的？什么是 TLAB、逃逸分析、标量替换？

    参考答案：新对象优先在Eden分配；大对象（超 PretenureSizeThreshold）直接进老年代；Eden 满触发 Minor GC，存活对象 age+1，超 MaxTenuringThreshold（默认15）晋升老年代；动态年龄判定（同年龄对象超 Survivor 一半也晋升）。TLAB：每个线程在 Eden 预分配小块，避免分配时竞争。逃逸分析：若对象未逃出方法，JIT 可在栈上分配/锁消除/标量替换（拆成基本类型），减少 GC 压力。

    核心考察点：对象分配全流程。

    深入追问（完整问答）：

    【Q52 追问 1】什么情况下对象会"逃逸"导致不能栈上分配？

    参考答案：当对象被外部引用（逃出当前方法作用域）就无法栈上分配，例如：① 作为返回值返回给调用方；② 被赋值给静态字段/全局集合；③ 作为参数传给可能逃逸的方法（或被存入线程共享结构）；④ 被其他线程访问。只有"对象生命周期完全局限在方法内、不被任何外部引用"才能逃逸分析判定为"未逃逸"，进而做栈上分配/标量替换。

    【Q52 追问 2】-XX:+DoEscapeAnalysis 默认开吗？

    参考答案：默认开启（server 编译器下）。逃逸分析是 JIT（C2）的优化，开启后才会做栈上分配、锁消除、标量替换。可通过 -XX:-DoEscapeAnalysis 关闭观察差异。注意：逃逸分析是"尽力而为"的优化，是否真的栈上分配由 JIT 自行判断，且只在热点方法触发，不能假设所有小对象都在栈上。

    Q53 【进阶】【通用能力补充】给一个 JVM 调优实战案例：某接口 RT 从 200ms 升到 2s，你如何定位并调优？

    参考答案（参考框架）：① 监控看 GC：发现老年代涨、Full GC 频繁且停顿长 → 疑内存/对象生命周期问题；② jstat -gcutil 确认；③ jmap -histo/MAT 找"大对象/缓存无上限"；④ 调优：调大堆、换 G1 并设目标停顿、修正"无限缓存"代码、对象池复用；⑤ 回归压测验证 RT 与 GC 频率。强调先定位根因再调参，不盲调 -Xmx。

    核心考察点：调优方法论（济南高级岗必考，简历有"排查线上问题"）。

    深入追问（完整问答）：

    【Q53 追问 1】如何判断 RT 升高是 GC 导致还是下游慢？

    参考答案：① 看监控分层：GC 日志（Full GC 频率/停顿）、下游 RT（链路追踪）、DB 耗时分别看；② 若 RT 升高同时有 Full GC 长停顿且 GC 后好转，多半是 GC；③ 若 GC 正常但下游依赖 RT 涨，是下游；④ 用 traceId 分段计时定位"卡在哪一跳"；⑤ 临时降级/摘除某依赖验证。原则是"用数据分层定位，不靠猜"。

    【Q53 追问 2】Full GC 后内存没降下来说明什么？

    参考答案：说明存在老年代对象无法被回收——即"内存泄漏"：这些对象仍被 GC Roots（如静态 Map、未remove 的 ThreadLocal、未关闭的资源、长生命周期缓存）强引用，GC 无能为力。每次 Full GC 都回收不掉，堆只涨不跌最终 OOM。此时应 jmap -histo + MAT 找"大对象 + Path to GC Roots"定位泄漏点。

    Q54 【高级】【简历依据：熟练-Spring】Spring 循环依赖三级缓存，为什么用三级而不是两级？构造器注入/原型 Bean 为什么解决不了？

    参考答案：三级：singletonObjects(成品) → earlySingletonObjects(早期引用) → singletonFactories(ObjectFactory)。关键在第三级工厂：它能延迟决定是否生成 AOP 代理——只有真正发生循环时才用工厂生成早期代理对象，避免无循环依赖也被提前代理、也避免重复创建代理。构造器注入在实例化阶段就要完整参数，此时对象尚未创建，三级缓存还没放入，故无解（直接抛 BeanCurrentlyInCreationException）；prototype 不缓存，每次新建，循环必死。

    核心考察点：循环依赖本质（简历 Spring 重点）。

    深入追问（完整问答）：

    【Q54 追问 1】@Lazy 怎么让构造器注入"绕过"循环依赖？

    参考答案：在循环的一方构造器参数上加 @Lazy，Spring 会注入一个延迟初始化的代理而非真实对象——构造时不立即创建依赖，等到首次真正使用时才初始化。这样构造阶段不必拿到完整依赖，循环被"延后"打破。代价是首次访问才真正创建，且依赖的是代理（需确保后续能拿到真实 Bean）。这是 Spring Boot 2.6+ 禁止普通循环依赖后的推荐解法。

    【Q54 追问 2】Spring Boot 2.6+ 为什么默认禁止循环依赖？

    参考答案：循环依赖往往是设计坏味道（职责不清、耦合过紧），Spring 团队认为不应鼓励。2.6 起 spring.main.allow-circular-references=false 默认关闭，启动即报错以促使开发者重构（提取第三类、用事件/接口解耦、调整职责）。保留 @Lazy 作为"确实必要时的逃生舱"。考察候选人是否理解"循环依赖是信号，而非特性"。

    Q55 【高级】【简历依据：熟练-SSM / 通用】AOP 用 JDK 动态代理还是 CGLIB？什么情况下事务/缓存注解"代理不生效"？

    参考答案：目标类有接口默认 JDK 代理（基于接口），无接口用 CGLIB（继承）。Spring Boot 2.0+ 默认 CGLIB（更统一）。代理不生效典型：① 同类自调用（A.a 调 A.b，b 上的 @Transactional 不走代理）；② 方法非 public（CGLIB 可代理但 Spring 限制）；③ 异常被 catch 未抛出；④ 内部 final 方法 CGLIB 无法织入；⑤ 异步 @Async 与 @Transactional 叠加时代理嵌套问题。

    核心考察点：代理机制与失效边界。

    深入追问（完整问答）：

    【Q55 追问 1】同一个 Bean 上 @Transactional + @Async，代理怎么套？需要怎么处理？

    参考答案：两者都是 AOP 代理，会在 Bean 外叠加。陷阱：若方法同时需要"事务"和"异步"，直接标注可能因为代理顺序/自调用导致其中一个不生效。处理：① 用 AopContext.currentProxy() 获取代理后调用（需 @EnableAspectJAutoProxy(exposeProxy=true)），避免自调用绕过代理；② 或将逻辑拆到两个 Bean，分别承担事务与异步；③ 注意 @Async 方法返回 Future 才能拿结果。本质是"多个代理叠加时，调用必须走代理而非 this"。

    【Q55 追问 2】如何单元测试验证事务/缓存注解生效？

    参考答案：① 用 @SpringBootTest 启动上下文，调用带注解的方法，断言"抛异常后 DB 是否回滚"（查库验证）；② 缓存注解：调用两次，断言第二次是否命中缓存（如 Redis 是否有值 / 方法实际执行次数）；③ 用 @Spy/@MockBean 验证代理被触发；④ 注意测试要跑在真实事务/缓存环境下，别用 @Transactional 测试事务回滚（会自相干扰）。核心是"用可观测的副作用证明注解真的织入了"。

    Q56 【高级】【通用能力补充】Spring 事务的 7 种传播行为，哪些场景用 REQUIRES_NEW / NESTED？

    参考答案：REQUIRED（默认，加入已有）、REQUIRES_NEW（挂起当前、开新事务，用于"日志记录必须落库不论主流程成败"）、NESTED（嵌套、可回滚到保存点，依赖 JDBC 保存点）、SUPPORTS/ NOT_SUPPORTED/ NEVER/ MANDATORY。场景：主流程失败但操作日志必须保留 → REQUIRES_NEW；子步骤可独立回滚不影响父 → NESTED。注意 NESTED 仅 JDBC 支持，JTA 不一定。

    核心考察点：事务传播与业务建模。

    深入追问（完整问答）：

    【Q56 追问 1】REQUIRES_NEW 与 NESTED 在"部分失败"语义上有什么区别？

    参考答案：REQUIRES_NEW：挂起外层事务、开全新独立事务，内层提交/回滚与外层完全无关（外层回滚不影响已提交的內层，内层回滚也不影响外层继续）；NESTED：在外层事务内开一个"嵌套保存点"，内层回滚只回滚到保存点（外层可继续），外层回滚则内层一起滚。语义：NEW=独立子任务（如日志必须留），NESTED=可局部回滚的子步骤（如批量中单项失败不影响其他项）。

    【Q56 追问 2】跨数据源时事务传播行为还有效吗？

    参考答案：单 PlatformTransactionManager 下才有效。跨数据源（多库/多 DataSource）时，Spring 默认的事务管理器只管一个库，另一个库的写操作不在同一事务里，"传播/回滚"无法跨库保证。解决方案：① 用 JTA（分布式事务管理器，重）；② 用 Seata（AT/TCC，见 Q76）；③ 用本地事务 + 消息最终一致。普通 @Transactional 跨库是"假事务"，必须点破。

    Q57 【中级】【简历依据：Spring 生态 / 通用】ApplicationEvent 事件机制（观察者模式）在你们项目怎么用？和直接方法调用、MQ 比有什么取舍？

    参考答案：用 ApplicationEventPublisher 发布、 @EventListener 监听，实现模块内解耦（如"订单支付后发通知/清缓存"）。与直接调用比：解耦、可异步（@Async）；与 MQ 比：仅进程内、无持久化与跨服务，适合轻量解耦。取舍：跨服务/需可靠投递用 MQ；同进程内轻量通知用事件，避免引入中间件复杂度。

    核心考察点：事件驱动取舍（呼应简历"消息/RocketMQ"选型意识）。

    深入追问（完整问答）：

    【Q57 追问 1】Spring 事件监听（@EventListener）异常会怎样？

    参考答案：默认同步监听（发布者与监听者同一线程），若监听方法抛异常，异常会冒泡回发布者，导致发布 publishEvent 的调用方收到异常——可能中断主流程。因此事件监听内部务必自己 try-catch 处理异常，或配置 AsyncUncaughtExceptionHandler（异步时）。否则"解耦的副作用"反而拖垮主流程，违背用事件的初衷。

    【Q57 追问 2】如何隔离事件监听（避免异常影响发布者）？

    参考答案：① 监听方法内 try-catch 吞掉/记录异常，不让其外抛；② 用 @Async 让监听异步执行（发布者不被阻塞、异常也不回流，但需配置异步异常处理器）；③ 关键事件用 MQ 替代 ApplicationEvent，获得持久化与失败重试；④ 对"可失败"的监听做降级。本质是"把事件当'尽力通知'，不为其失败买单"。

    Q58 【高级】【通用能力补充】BeanFactory 与 ApplicationContext 区别？ApplicationContext 启动时做了什么（对比懒加载）？

    参考答案：BeanFactory 基础容器，懒加载（用时才创建）；ApplicationContext 是其超集，启动时立即实例化单例（eager）、提供事件、国际化、AOP、环境抽象等。启动时预实例化可早点暴露配置错误，但启动慢、内存占用高。生产一般接受 eager 以换运行期稳定；超大应用可配懒加载关键 Bean。

    核心考察点：容器层次与启动行为。

    【Q58 追问 1】ApplicationContext 启动慢怎么优化？

    Q59 【高级】【简历依据：熟悉-MySQL】MVCC 是怎么实现"可重复读"的？ReadView / undo log 的作用？

    参考答案：MVCC 靠隐藏事务 ID（DB_TRX_ID）+ 滚动指针（DB_ROLL_PTR）+ undo log 实现。每行有多个版本，事务读时生成 ReadView（记录活跃事务集合），按规则（trx_id 是否可见）沿 undo 链找到对自己可见的版本，从而不加锁实现"可重复读"。RR 下 ReadView 在事务首次读时生成（整个事务复用），RC 下每次读都生成（故不可重复读）。

    核心考察点：MVCC 原理（济南中级以上必考）。

    深入追问（完整问答）：

    【Q59 追问 1】RR（可重复读）下幻读靠什么彻底解决？

    参考答案：MVCC 解决"快照读"的不可重复读，但当前读（SELECT ... FOR UPDATE / UPDATE）仍可能幻读。InnoDB 在 RR 下靠 Next-Key Lock（记录锁 + 间隙锁）彻底防幻读——锁住满足条件的范围，阻止其他事务在该范围插入新行。注意：若隔离级别降为 RC 或显式关闭 gap lock，则只能靠应用层防幻读。

    【Q59 追问 2】长事务对 undo log / 版本链有什么危害？

    参考答案：MVCC 靠 undo log 维护历史版本，而 undo log 只有在没有任何活跃事务需要它时才能被 purge 清理。一个长事务会一直"钉住"它开启时刻之后的所有旧版本，导致 undo log 与版本链不断堆积、膨胀，进而：① 回滚段占用暴涨；② 其他查询沿长版本链回溯变慢；③ 可能拖慢整个实例。因此生产要避免长事务（拆小、控制持有时间）。

    Q60 【高级】【简历依据：熟悉-MySQL】InnoDB 的锁有哪些？间隙锁、Next-Key Lock 如何防幻读？什么会把锁放大？

    参考答案：行锁（Record）、间隙锁（Gap，锁区间防插入）、Next-Key（Record+Gap，左开右闭）。RR 下默认用 Next-Key 防幻读。锁放大陷阱：① 非索引列更新 → 行锁升级为表锁；② 范围更新锁整个范围；③ 事务未提交持锁久；④ select ... for update 范围过大。优化：索引命中、缩小事务、控制更新范围。

    核心考察点：锁机制与线上并发安全（简历"参与查询优化"延伸）。

    深入追问（完整问答）：

    【Q60 追问 1】如何查看当前 InnoDB 的锁等待？

    参考答案：① 老版本：information_schema.INNODB_LOCKS（持有锁）、INNODB_LOCK_WAITS（等待关系）；② 新版本（8.0）：performance_schema.data_locks、data_lock_waits；③ sys.innodb_lock_waits 视图给出"谁被谁阻塞、等什么锁、SQL 是什么"的易读结果；④ SHOW ENGINE INNODB STATUS 看 LATEST DETECTED DEADLOCK 与锁信息。结合业务定位"哪个事务持锁不释放"。

    【Q60 追问 2】死锁如何被自动检测与回滚？

    参考答案：InnoDB 内置死锁检测（wait-for graph），发现循环等待即判定死锁，选一个代价最小的事务作为"牺牲者"回滚（ER_LOCK_DEADLOCK），让其他事务继续。默认开启（innodb_deadlock_detect=ON）。但检测有开销，高并发下可关掉改依赖 lock_wait_timeout 超时退出（治标）。应用层应统一加锁顺序、缩短事务、重试死锁，从源头减少死锁。

    Q61 【高级】【通用能力补充】redo log / undo log / binlog 各解决什么？两阶段提交如何保证崩溃恢复一致？

    参考答案：redo log（InnoDB，物理日志）保证持久性，崩溃后重放；undo log 支持原子性/回滚/MVCC；binlog（Server 层，逻辑日志）用于主从复制/时间点恢复。两阶段提交：① 写 redo（prepare）② 写 binlog ③ redo 提交。崩溃恢复时：若 binlog 完整则提交，否则回滚，保证两者一致。这是"MySQL 为什么能崩而不丢数据"的核心。

    核心考察点：日志体系（高级岗根因理解）。

    深入追问（完整问答）：

    【Q61 追问 1】为什么 redo log 用循环写、binlog 用追加写？

    参考答案：redo log 是 InnoDB 物理日志、固定大小循环写（写满覆盖旧段），因为它只服务于"崩溃后重放最近未刷盘的修改"，旧日志在 checkpoint 后即可丢弃，循环写高效省空间。binlog 是 Server 层逻辑日志、用于主从复制/时间点恢复，必须追加写、永久保留（按文件滚动），以便从库持续消费、按时间点回放任意历史，不能覆盖。两者定位不同决定写方式不同。

    【Q61 追问 2】sync_binlog 与 innodb_flush_log_at_trx_commit 如何取舍性能与可靠？

    参考答案：innodb_flush_log_at_trx_commit=1（每次事务刷盘 redo）+ sync_binlog=1（每次事务刷盘 binlog）最可靠（双 1，崩溃不丢），但性能最低（每次写都 fsync）；调为 0/2 提升吞吐但可能丢最近事务。金融/支付用"双 1"；对一致性要求低的业务可放宽换性能。取舍核心："能接受丢多少数据"决定刷盘策略。

    Q62 【进阶】【通用能力补充】分库分表怎么做？分片键怎么选？跨分片查询/分布式事务怎么处理？

    参考答案（参考框架）：垂直分（按业务/冷热拆表），水平分（按分片键路由）。分片键选高频且分布均匀的字段（用户 ID/订单 ID），用取模/范围/一致性哈希。难点：① 跨分片 join → 冗余/异构（ES）；② 分布式事务 → Seata/TCC/消息最终一致；③ 跨片分页/聚合 → 中间件（ShardingSphere）或应用层归并；④ 分片键变更极难。务必先评估是否真到瓶颈（读写分离/索引优化常能扛住）。

    核心考察点：分片架构权衡（济南大表/日志场景相关）。

    深入追问（完整问答）：

    【Q62 追问 1】订单按用户 ID 分片后，按商家维度查询怎么办？

    参考答案：分片键固定后"非分片键查询"成难题。方案：① 异构索引表/全局二级索引——另建一张"按商家 ID 分片"的映射表（记录 商家→订单ID），查商家时先查映射表拿到订单 ID 再回原分片；② 双写/冗余，把订单关键信息按商家维度也存一份；③ 走 ES/数仓做多维检索（OLAP）；④ 业务上限制"商家查询"走专用检索服务。本质是"用空间/冗余换多维查询能力"。

    【Q62 追问 2】ShardingSphere 与 MyCat 区别？

    参考答案：ShardingSphere（JDBC 层/Proxy 多种形态）是轻量、可嵌入的分库分表中间件，应用侧引入依赖即可，对代码侵入小、性能高（JDBC 直连）；MyCat 是独立代理（Proxy），应用像连 MySQL 一样连 MyCat，部署独立但多一跳、运维成本高。选型：想低侵入高性能选 ShardingSphere-JDBC；想集中治理/多语言接入选 Proxy 类（MyCat/ShardingSphere-Proxy）。先论证是否真要分片（读写分离常够用）。

    Q63 【高级】【通用能力补充】MySQL 主从复制原理？读写分离下"主从延迟"导致读不到刚写的数据怎么办？

    参考答案：binlog 异步复制到从库 relay log 再回放（默认异步，可半同步）。主从延迟来源：从库回放慢、大事务、网络。读不到新数据的应对：① 写后强制读主（关键路径，如"刚下单查订单"）；② 写时标记"该用户走主库"一段时间；③ 半同步复制降低延迟；④ 业务容忍最终一致。关键：区分"强一致读"与"普通读"。

    核心考察点：复制与一致性（简历多端/订单场景延伸）。

    深入追问（完整问答）：

    【Q63 追问 1】半同步复制会丢数据吗？

    参考答案：半同步（semi-sync）要求主库提交时至少一个从库收到 binlog 并 ack才返回成功，相比异步大幅降低丢数据概率。但仍有窗口风险：① 主库在"已提交但未收到 ack 前"崩溃（超时降级为异步）可能丢；② ack 后、从库回放前主库宕，从库接管后可能缺该事务（取决于是否等回放）。金融级用"增强半同步 + 无损复制"进一步逼近不丢，但理论上极端故障仍有极小风险，需配合对账兜底。

    【Q63 追问 2】并行复制（MTS）如何提升从库回放？

    参考答案：传统从库单线程回放，主库并发写入时从库易延迟。MySQL 并行复制（MTS）按组提交（LOGICAL_CLOCK）/ 库（DATABASE）维度把无冲突的事务并行回放，提升从库吞吐、降低延迟。配置 slave_parallel_workers 等参数。本质是把"单线程重放"变成"按依赖关系并行重放"，缩小主从延迟（呼应 Q63 主从延迟治理）。

    Q64 【高级】【简历依据：参与查询优化】除了加索引，还有哪些"查询优化"手段？（避免只答索引）

    参考答案（参考框架）：① 改写 SQL（子查询转 join、避免 select *、减少 or/函数包裹列）；② 深分页用"游标/延迟关联"（where id>lastId limit N）；③ 冷热分离/归档历史数据；④ 读写分离分担；⑤ 用覆盖索引避免回表；⑥ 物化视图/冗余字段减少实时计算；⑦ 大结果集导出走异步+游标（见 Q31）。强调：优化要先 explain 定位瓶颈类型（扫描多？排序？临时表？），再对症。

    核心考察点：优化手段广度（对应简历"参与查询优化"，逼出真实经验）。

    深入追问（完整问答）：

    【Q64 追问 1】Using temporary 通常因什么产生？

    参考答案：MySQL 需建临时表才能完成查询时会出现，常见诱因：① GROUP BY / DISTINCT 无索引、需先分组；② ORDER BY 与 GROUP BY 列不一致（无法利用同一索引）；③ 子查询/UNION 需物化；④ JOIN 无合适索引导致中间结果物化。优化：建合适索引让分组/排序走索引、避免 SELECT DISTINCT、改写 SQL 减少物化。结合 explain 的 Extra 定位。

    【Q64 追问 2】一张 5000 万行表 COUNT(*) 慢怎么优化？

    参考答案：COUNT(*) 在 InnoDB 要逐行统计（无缓存），大表很慢。优化：① 近似值——SHOW TABLE STATUS 的 Rows（估算）或 EXPLAIN 的 rows（非精确）；② 汇总表/计数器——用独立表记录行数、增删时维护（或定时任务更新）；③ 缓存计数（Redis INCR）；④ 若只需"是否存在/是否超阈值"，用 EXISTS/LIMIT 1 代替 count；⑤ 归档冷数据减小表。核心是"别对大表实时 count"。

    F. 缓存 Redis（深入）

    Q65 【高级】【简历依据：Redis】RDB、AOF、混合持久化各自代价？金融/重要数据怎么配？

    参考答案：RDB：定时快照，恢复快、体积小，但丢最后一次快照后数据；AOF：追加命令，appendfsync=everysec 最多丢 1s，文件大、恢复慢；混合持久化（Redis 4.0+，AOF 文件含 RDB 头+增量）兼顾。重要数据：aof-use-rdb-preamble yes + AOF everysec + 定期 RDB；极高可靠用 always（性能差）。济南金融/电力场景偏可靠，倾向混合 + 从库。

    核心考察点：持久化取舍（简历 Redis 实践延伸）。

    深入追问（完整问答）：

    【Q65 追问 1】AOF 重写（rewrite）期间会不会阻塞？

    参考答案：AOF rewrite 通过 fork 子进程完成，父进程继续服务、子进程读内存快照写新 AOF，因此正常不阻塞主线程。但 fork 本身在大数据集时会有短暂停顿（复制页表），且若开启 aof-rewrite-incremental-fsync 可平滑写盘。风险点：rewrite 期间内存占用翻倍（写时复制 Copy-On-Write），需留足内存。总体 rewrite 对在线服务影响可控。

    【Q65 追问 2】主从切换后 AOF 怎么续？

    参考答案：主从切换（如哨兵/Cluster 选新主）后，新主接管并继续写自己的 AOF；原主恢复后通常作为从库重新全量/部分同步新主数据，其旧 AOF 不再作为主用。关键是切换后客户端连接指向新主、复制链路重建。对数据可靠性：新主若开启 AOF（everysec + RDB 前缀混合），崩溃后能从自身 AOF 恢复，不依赖旧主日志。

    Q66 【高级】【通用能力补充】Redis 高可用三件套：主从、哨兵、Cluster 各自解决什么？Cluster 的槽怎么分配？

    参考答案：主从（读写分离、容灾，故障需人工切）、哨兵（自动故障转移+监控）、Cluster（16384 槽分片、多主多从、自动故障转移，支持大数据量高并发）。Cluster 槽：key 经 CRC16 % 16384 映射到槽，槽再分给节点；扩缩容靠 reshard 迁移槽。注意：Cluster 下多 key 操作需同一槽（用 hash tag {user1} 强制同槽）。

    核心考察点：高可用架构（济南高可用要求）。

    深入追问（完整问答）：

    【Q66 追问 1】Cluster 下 MSET 多 key 跨槽报错怎么解决？

    参考答案：Redis Cluster 要求一个命令的所有 key 必须在同一槽，否则 CROSSSLOT 报错。MSET 多 key 若分散在不同槽就会失败。解决：① 用 hash tag——给 key 加 {tag}（如 user:{1001}:name、user:{1001}:age），Cluster 只对 {} 内部分做 CRC16 取模，保证同 tag 的 key 落同一槽；② 或改用多次单 key 命令（牺牲原子性）；③ 或客户端分批（同一槽的放一批）。

    【Q66 追问 2】gossip 协议在 Cluster 里干什么？

    参考答案：Redis Cluster 节点间用 gossip（流言）协议交换集群状态（节点上线/下线、槽分配、故障怀疑等）——每个节点定期随机 ping 几个其他节点，收到 pong 后更新本地视图并继续传播。它让集群去中心化、最终一致地感知拓扑变化，配合故障检测（多数派确认宕机才真正 failover）。gossip 容错好、扩展性强，但状态传播有延迟（秒级）。

    Q67 【进阶】【通用能力补充】线上 Redis 热 key / 大 key 怎么发现与治理？给实战方案。

    参考答案（参考框架）：发现：监控（redis-cli --hotkeys、Proxy/AGENT 上报、OBJECT 统计）、业务埋点。热 key：本地缓存+随机过期、key 打散（副本 key_01..10 分流）、限流。大 key（如大 Hash/List 几 MB）：避免 DEL 阻塞（用 UNLINK 异步或 HSCAN 分批删）、拆分结构、控制单条大小。治理要进发布前评审（防止写入大 key）。

    核心考察点：缓存实战治理（对应简历"排查线上问题"）。

    深入追问（完整问答）：

    【Q67 追问 1】大 key 删除为什么用 UNLINK 而非 DEL？

    参考答案：DEL 是同步删除，大 key（如几 MB 的 Hash/List、百万元素）删除时要释放大量内存，会阻塞主线程造成卡顿（甚至秒级）。UNLINK（Redis 4.0+）是异步惰性删除，主线程只把 key 从字典摘除，实际内存释放交给后台线程（bio）慢慢做，不阻塞请求。生产删大 key 一律用 UNLINK，或 HSCAN/SSCAN 分批删除。

    【Q67 追问 2】热 key 本地缓存如何保证与 Redis 一致性？

    参考答案：本地缓存（Caffeine）挡热点，但多实例下与 Redis 可能不一致。策略：① 短 TTL——本地缓存设很短过期（如秒级），过期后回源 Redis，保证最终收敛；② 主动失效广播——Redis 更新时通过 Pub/Sub 或配置中心通知各实例清本地缓存；③ 接受"秒级不一致"（读多写少热点可接受）；④ 写时"先更 Redis + 删本地"（或用 Canal 监听 binlog 清本地，见 Q68）。核心是"短 TTL + 失效通知"双保险。

    Q68 【高级】【简历依据：Redis / 通用】多级缓存（本地 Caffeine + Redis）怎么设计？缓存与 DB 一致性深入方案？

    参考答案（参考框架）：本地缓存挡热点（毫秒级、抗 Redis 抖动），Redis 挡全局，DB 兜底；更新时"删本地 + 删 Redis + 更 DB"（可借助 canal/binlog 广播清本地）。一致性：强一致不可能；常用"Cache-Aside（先更 DB 再删缓存）+ 延迟双删 + 消息/订阅兜底"，关键业务用 binlog（Canal）异步清缓存，容忍秒级不一致。要点：删除而非更新缓存（避免并发写乱序）。

    核心考察点：多级缓存与一致性（简历缓存实践进阶）。

    深入追问（完整问答）：

    【Q68 追问 1】本地缓存在多实例下如何失效同步？

    参考答案：方案：① 短 TTL（最简单，靠时间自然收敛，容忍短暂不一致）；② 消息广播——更新时用 Redis Pub/Sub 或 MQ 发"清缓存"事件，各实例订阅后删本地；③ 配置中心/Bus 广播刷新；④ Canal 订阅 binlog——数据变更自动触发各实例清本地（见下）；⑤ 一致性要求高的关键数据"写后强制读主/查源"绕过本地。选型看一致性容忍度与复杂度。

    【Q68 追问 2】Canal 订阅 binlog 延迟导致脏读怎么办？

    参考答案：Canal 异步解析 binlog 清缓存，存在"DB 已更新、缓存还没清"的短暂窗口，可能读到旧值。缓解：① 写后先删缓存（Cache-Aside）+ Canal 兜底，双重保障；② 缩短 Canal 消费延迟（调优位点、并发消费）；③ 关键路径接受"最终一致"或读主；④ 用"延迟双删"覆盖窗口。本质是承认异步有延迟，用"删缓存 + 兜底"把不一致窗口压到最小。

    Q69 【高级】【通用能力补充】maxmemory-policy 各策略区别？生产怎么选？内存达到上限写不进会怎样？

    参考答案：noeviction（默认不淘汰、写报错）、allkeys-lru/volatile-lru（最近最少）、allkeys-lfu/volatile-lfu（最不常使用，4.0+ 更准）、allkeys-random、volatile-ttl。生产缓存用 allkeys-lru（或 lfu 抗突发）；带 TTL 的会话用 volatile-*。noeviction 下写被拒会触发业务失败，故必须设合理 maxmemory 与策略。

    核心考察点：内存淘汰实战。

    深入追问（完整问答）：

    【Q69 追问 1】LRU 与 LFU，在"偶发大热点"场景谁更稳？

    参考答案：LFU（最不常使用）更稳——LRU 只看"最近访问"，一次性的大批量扫描（如全表遍历）会把真正的热点全挤出去（缓存污染）；LFU 按"访问频率"淘汰，偶发扫描的低频 key 不会冲掉长期高频热点。Redis 4.0+ 的 allkeys-lfu 适合此类场景。volatile-lfu 则只对带过期键生效。代价：LFU 需维护频率计数、实现略重。

    【Q69 追问 2】volatile-lru 但 key 都没设过期时间会怎样？

    参考答案：volatile-* 系列策略只对带 TTL 的 key 做淘汰。若所有 key 都没设过期（都是永久 key），volatile-lru 发现"没有可淘汰的键"，于是什么都不淘汰——内存到 maxmemory 上限后，新写入直接返回 OOM 错误（写被拒），业务失败。因此用 volatile-* 必须确保大部分 key 有 TTL；否则应改用 allkeys-*。

    G. 消息队列（深入）

    Q70 【高级】【简历依据：RabbitMQ/RocketMQ】如何保证消息"顺序性"？你们项目（如操作日志、订单状态）需要顺序吗？

    参考答案：顺序靠"相同业务 key 落同一分区/队列 + 单消费者串行"。Kafka/RocketMQ 按 key 路由到固定 partition/queue；RabbitMQ 用单队列单消费者。但顺序会牺牲并发。判断是否需要：订单状态流转（待支付→已支付→完成）通常需要顺序，操作日志追加通常不需要。取舍：非必要不强行保序（用业务状态机兜底幂等更稳）。

    核心考察点：顺序性成本与必要性（简历消息实践延伸）。

    深入追问（完整问答）：

    【Q70 追问 1】RocketMQ 顺序消息消费失败会阻塞后续吗？

    参考答案：会——顺序消息要求同队列串行消费，若某条消息消费失败且不跳过，消费者会一直重试该条，后续消息被阻塞（队列停摆），严重影响吞吐。应对：① 重试设上限，超限进死信；② 对"可跳过"的业务异常做记录后继续；③ 区分"可恢复"（网络抖动，重试）与"不可恢复"（数据错误，进死信）避免无谓阻塞。顺序与可用性要权衡。

    【Q70 追问 2】既要保序又要并发，怎么折中？

    参考答案：把"需要顺序"的粒度细化——不是整条流保序，而是"同一业务 key（如同一订单 ID）保序"，不同 key 之间可并行。实现：按 key 路由到不同分区/队列（不同 key 并发），同 key 落同分区串行。这样在"订单级有序"的前提下最大化并发，是顺序与吞吐的常用折中（呼应 Q70 基础题）。

    Q71 【进阶】【通用能力补充】MQ 消息积压了（几百万条），怎么应急与根治？

    参考答案（参考框架）：应急：① 临时扩容消费者（加机器/线程），提高并行度；② 若是消费者慢（如同步调下游），先降级非核心逻辑、异步化；③ 积压严重可临时建"转发队列"分流。根治：① 消费幂等 + 批量；② 监控积压告警；③ 限流保护下游；④ 必要时跳过非重要消息（死信）。切忌盲目加消费者却不提升下游能力。

    核心考察点：积压治理（济南后台高吞吐场景）。

    深入追问（完整问答）：

    【Q71 追问 1】消费者加了但积压不降，可能是什么原因？

    参考答案：加消费者不灵通常是因为瓶颈不在消费端并发数：① 单分区/单队列限制——Kafka/Rabbit 单分区只能一个消费者消费，加再多也白搭（需增分区）；② 下游慢（DB 慢 SQL/锁、外部接口超时）拖垮消费，消费 TPS 上不去；③ 消费逻辑单线程、或每条处理耗时过长；④ 消费者频繁重平衡（rebalance）；⑤ 消费失败无限重试堵住。先定位瓶颈（下游/分区/单条耗时）再扩。

    【Q71 追问 2】如何评估需要多少消费者？

    参考答案：粗略公式：所需消费者数 ≈ 积压量 / (单消费者 TPS × 预计消化时间)，或更准地：先压测出单消费者稳定消费 TPS（假设下游能扛），再用 目标TPS / 单消费者TPS 得出实例数，并预留 buffer。关键约束是下游系统的处理能力（DB/接口），消费者再多下游扛不住也没用——所以要先扩容下游或优化消费逻辑。

    Q72 【高级】【简历依据：消息 / 通用】消费端幂等架构怎么做？除了唯一 ID 去重还有哪些手段？

    参考答案（参考框架）：① 业务唯一键 + 去重表/Redis SETNX（处理中标记）；② 数据库唯一索引兜底（重复插入失败）；③ 状态机（已处理直接返回）；④ 版本号/乐观锁。架构上：消费前查"是否已处理"，处理后落标记；对"至少一次"投递天然兼容。结合简历"操作日志"：日志去重可用 (bizId, type) 唯一索引。

    核心考察点：幂等架构化（简历操作日志场景）。

    深入追问（完整问答）：

    【Q72 追问 1】Redis 去重与 DB 唯一索引如何配合？

    参考答案：Redis 挡大部分、DB 兜底。流程：消费前先 SETNX(dedupKey, 1)（带 TTL），成功才继续处理；同时业务落库时DB 唯一索引（如 (bizId, type)）做最后防线——即使 Redis 因过期/故障漏挡，DB 唯一键冲突也会让重复插入失败、catch 后返回已处理。两层结合兼顾性能（Redis 快）与可靠（DB 保底），避免"只靠 Redis 丢数据"或"只查 DB 慢"。

    【Q72 追问 2】分布式下去重存储用 Redis 还是 DB？

    参考答案：看诉求：① Redis——高性能、天然过期、适合高并发去重，但宕机/过期可能丢标记（需配合 DB 兜底，且过期时间要覆盖"重复窗口"）；② DB 唯一索引——最可靠、持久，但每次查/插有 IO 开销，高并发下有锁竞争。工程实践：高并发用 Redis 前置去重 + DB 唯一键兜底；对"绝对不能重复"的关键业务以 DB 为准。本质是"性能 vs 可靠"的取舍。

    Q73 【高级】【通用能力补充】Kafka / RabbitMQ / RocketMQ 选型对比？简历只用后两者，你怎么看引入 Kafka 的取舍？

    参考答案（参考框架，Kafka 虽简历未用但属通用中高级要求）：Kafka：超高吞吐、分区、日志/流处理首选，但运维复杂、延迟略高；RabbitMQ：协议丰富、路由灵活、易用，适合业务解耦；RocketMQ：Java 生态、事务/顺序消息、堆积能力强，适合金融/电商。取舍：已有 Rabbit+Rocket 若够用不必强引 Kafka；只有"海量日志/流计算"才值得引入，否则增加运维与一致性复杂度。

    核心考察点：MQ 选型权衡（对应简历"两个 MQ"的反思）。

    深入追问（完整问答）：

    【Q73 追问 1】为什么项目可能同时用 RabbitMQ + RocketMQ（按场景分层）？

    参考答案：合理分层：RabbitMQ 胜在协议丰富、路由灵活、易用，适合一般业务解耦（如通知、事件）；RocketMQ 胜在事务/顺序消息、海量堆积、Java 生态，适合订单/金融等强一致高可靠链路。两者职责不同，各司其职。但也要诚实地评估"能否收敛到一个"——若只是图省事各引一个，就是过度设计，维护两套 MQ 成本不低。

    【Q73 追问 2】引入第三个 MQ（如 Kafka）的维护成本？

    参考答案：每多一个 MQ 就多一套：部署运维、监控告警、故障排查、客户端依赖、人员学习、容量规划。Kafka 适合"海量日志/流计算"，若项目并无此类需求，引入只为"技术储备"就是成本大于收益。建议：先用好已有的 Rabbit+Rocket，确有"高吞吐日志/流处理"刚需再引入 Kafka，且要评估团队能否 hold 住三套中间件的复杂度。

    Q74 【高级】【通用能力补充】消息轨迹/消费重试机制怎么设计？失败多次后怎么办？

    参考答案：消息轨迹：在发送/存储/消费各节点打点（msgId + 状态 + 时间）落库/ES，便于排查"丢了还是消费慢"。重试：消费失败按指数退避重试（MQ 自带或业务实现），超过阈值进死信队列（DLQ）；DLQ 人工/定时补偿。关键：重试必须幂等（否则重复副作用），且区分"可恢复"（网络抖动）与"不可恢复"（数据错误，直接进死信）。

    核心考察点：可靠性工程（呼应简历"操作日志集成"）。

    【Q74 追问 1】死信消息人工处理后，如何"补采"回主流程？

    参考答案：DLQ 里的消息经人工修复（如修正数据、补下游）后，需要重新进入正常处理。方式：① 写脚本/工具把 DLQ 消息重新投递到原业务队列（或专门的"重处理队列"）；② 或用管理台手动重发；③ 补采时要防重复副作用（幂等），确保重放不会造成二次影响；④ 记录补采日志便于审计。关键是"DLQ 不是终点，要有闭环的补采机制"。

    【Q74 追问 2】重试风暴（大量消息连续失败）怎么熔断？

    参考答案：大量消息同时失败会触发疯狂重试，进一步压垮已故障的下游，形成风暴。熔断：① 限流/暂停消费——检测到失败率超阈值就暂停拉取或降速；② 指数退避 + 随机 jitter，避免"同时重试同时挂"的共振；③ 快速进 DLQ 而非无限重试；④ 对下游做熔断（Sentinel/Hystrix），下游病了就快速失败不再打；⑤ 告警人工介入。核心："失败要快速隔离，别用重试把火点更大"。

    【Q75 追问 1】熔断的"半开（Half-Open）"状态是干什么的？

    参考答案：熔断三态：关闭（正常）→ 打开（错误率超阈值，快速失败）→ 半开（经过熔断时长后，放少量试探请求）。半开状态放一两个请求探活，若成功则恢复"关闭"（服务好了），失败则回到"打开"（继续熔断）。它避免了"永久熔断"或"盲目恢复"，用最小代价探测依赖是否康复，是熔断器的核心自愈机制。

    【Q75 追问 2】Sentinel 的规则存在哪？

    参考答案：Sentinel 支持多种 DataSource（规则源）：① 默认内存（重启丢失）；② 文件（FileDataSource，本地持久）；③ Nacos / ZooKeeper / Apollo（动态推送，生产推荐）——规则改了实时推送到各实例；④ 控制台推送（经 DataSource 持久化）。生产必须用"外部动态数据源"（如 Nacos），否则规则只在内存、重启即失效、且无法统一管控。

    Q76 【进阶】【简历依据：分布式 / 通用】Seata 的 AT 模式原理？和 TCC、本地消息表怎么选？

    参考答案（参考框架）：AT：自动对 SQL 解析生成 undo/redo 日志，一阶段提交本地事务+记录，二阶段全局提交/回滚（异步删日志/按 undo 反向）；对业务侵入小。TCC：手动 Try/Confirm/Cancel，性能好但侵入大，适合强一致核心链路。本地消息表/事务消息：最终一致，简单但前提是"本地事务+消息"原子。选型：一般业务用 AT（性价比），强一致核心（扣款）用 TCC，跨系统异步用消息最终一致。

    核心考察点：分布式事务方案权衡（简历"多课程合单/订单"延伸）。

    【Q76 追问 1】Seata AT 模式的 undo log 表在哪？全局锁冲突怎么办？

    参考答案：AT 模式在每个参与的业务库里建 undo_log 表，记录数据修改前后的镜像，用于二阶段回滚。全局锁由 TC 管理（存在 TC 的存储，如 DB/Redis），防止"其他事务在全局事务提交前改了同一行"。冲突处理：② 若获取全局锁失败（被别的全局事务占着），本地事务会重试/抛异常，应用需处理超时与重试；② 减小事务粒度、缩短持有时间降低冲突。AT 对业务侵入小但依赖全局锁，高冲突场景要谨慎。

    【Q76 追问 2】Seata 的 TC（事务协调器）单点怎么解决？

    参考答案：TC 是 Seata 的中心节点，单点有风险。解决：① TC 支持集群部署（多节点），通过注册中心（如 Nacos）做服务发现与选主；② TC 的状态（全局/分支事务）存到共享存储（DB/Redis），任一 TC 实例宕机，其他节点能接手（因为状态在外存、不丢）；③ 客户端配置多个 TC 地址做高可用。这样避免"TC 挂了全链路分布式事务不可用"。

    Q77 【高级】【通用能力补充】链路追踪（SkyWalking / Zipkin）原理？traceId 怎么跨线程、跨服务传递？

    参考答案：基于埋点 + 上下文传播：请求入口生成 traceId+spanId，通过 HTTP header（如 traceparent）、MQ 消息属性、线程上下文（ThreadLocal/TTL）向下游与服务间传递，各节点上报形成调用树。SkyWalking 用 Java agent 字节码增强免侵入。价值：定位慢调用、依赖、故障根因（呼应简历"排查线上问题"）。

    核心考察点：可观测性（济南中高级岗加分）。

    【Q77 追问 1】异步线程（线程池）下 traceId 丢了怎么补？

    参考答案：traceId 通常存 ThreadLocal，线程池复用/新线程会让它丢失。补法：① 用 TransmittableThreadLocal（TTL）装饰任务，提交时快照、执行时设入（呼应 Q47）；② 或在线程池的 beforeExecute/afterExecute 中手动从父任务传递 traceId；③ SkyWalking 等 agent 对线程池有自动增强（或需配 apm-toolkit-trace 的 TraceCrossThread）；④ 跨服务靠 HTTP header / MQ 属性传递。核心是"异步边界必须显式传递上下文"。

    参考答案：全量采集成本高（存储/网络/性能），通常采样：① 低流量服务可全采（100%）；② 高流量按 QPS 比例采样（如 10%~20%）或用"自适应采样"；③ 对错误/慢请求强制采样（异常 100% 采，便于排查）；④ 头部采样（入口决定整条链采不采）避免半截链。建议：常态采样 + 异常/慢链路保采，平衡成本与可用性。

    【Q80 追问 1】Nacos 临时实例为什么是 AP（Distro 协议）？

    参考答案：注册中心的核心诉求是可用性——服务注册/发现即使部分节点故障也要能读写，不能因追求强一致而拒绝注册。Nacos 对临时实例用 Distro（AP 协议）：数据在节点间异步复制，不要求多数派确认，高可用优先，牺牲强一致（可能短暂读到旧实例列表）。这与 Eureka 的 AP 取向一致。对"配置"等需强一致的用 CP（Raft）。取舍符合 CAP 中"P 必选，注册场景选 AP"。

    【Q80 追问 2】Raft 脑裂下如何保证不双写（不丢已提交日志）？

    参考答案：Raft 靠任期（term）+ 多数派（quorum）保证：① 选举必须获多数派投票，而一个任期内每张选票唯一，因此不可能同时选出两个 Leader（两个 Leader 需各自多数派，而多数派必相交，矛盾）；② 日志提交需"复制到多数派"才算 committed，脑裂后少数派无法提交新日志、且旧 Leader 失去多数派后其未提交日志不会被认作已提交；③ 新 Leader 含所有 committed 日志（选举限制：候选者日志必须至少和多数派一样新）。从而"已提交不丢、不双写"。

    Q81 【高级】【简历依据：Nacos / 通用】Nacos 作为配置中心，动态刷新怎么实现的？灰度/多环境配置怎么管？

    参考答案：客户端监听配置（长轮询/Long Polling），服务端变更推送，客户端用 RefreshScope + @RefreshScope 或 NacosConfigManager 热更新 Bean 属性（底层发 RefreshEvent 重建 Bean）。灰度：Nacos 支持按 IP/标签灰度发布；多环境用 namespace（环境隔离）+ group（业务分组）+ dataId（配置项）。避免把密钥明文放配置（用 KMS/加密）。

    核心考察点：配置中心实战（简历 Nacos 延伸）。

    深入追问（完整问答）：

    【Q81 追问 1】@RefreshScope 的 Bean 刷新会有瞬时空窗吗？

    参考答案：会——@RefreshScope 刷新时，Spring 会销毁旧 Bean 实例并重建新实例来注入新配置。在"销毁旧、创建新"的瞬间，若有请求进来可能短暂拿到旧值、或遇到重建中的状态不一致（尤其构造慢的 Bean）。缓解：① 配置变更多在低峰期；② 用不可变配置 + 优雅刷新；③ 接受极短窗口（通常毫秒级）。理解"刷新不是零成本、有重建过程"。

    参考答案：Nacos 配置中心保留历史版本，热更新出问题可：① 在 Nacos 控制台"回滚"到上一可用版本，客户端监听会重新拉取、自动刷新；② 若刷新导致 Bean 重建失败，应用可能报错，需快速回滚配置 + 重启（最坏）；③ 灰度发布（按 IP/标签）先小范围验证再全量，降低回滚面。核心是"配置也要版本化、可回滚、可灰度"。

    Q82 【进阶】【通用能力补充】全链路性能优化思路？从接入层到 DB 你怎么逐层"找瓶颈、定方案"？

    参考答案（参考框架）：分层：① 接入/网关（连接数、限流、压缩）；② 应用（线程池、锁、对象分配、GC）；③ 缓存（命中率、大 key）；④ 中间件（MQ 积压、Redis RT）；⑤ DB（慢 SQL、锁等待、连接池）。方法：压测定位瓶颈层 → 分段计时/链路追踪定位具体点 → 单点优化 → 回归对比。原则：先测后优、避免过早优化、量化收益。

    核心考察点：系统级优化观（济南高级岗核心）。

    深入追问（完整问答）：

    【Q82 追问 1】如何确定瓶颈在应用还是 DB？

    参考答案：① 链路追踪看各段耗时，RT 大头在 DB 调用还是应用自身计算一目了然；② 分指标看：DB 连接池等待数高 → 数据库侧或连接不够；应用 CPU 满 → 计算/锁；③ 隔离验证——临时把某 DB 查询换成 mock，RT 是否骤降（降则说明 DB 是瓶颈）；④ 看慢查询日志/锁等待（DB 侧证据）vs 火焰图（应用侧热点）。用"分层数据"而非直觉定位。

    【Q82 追问 2】优化后如何防止回归？

    参考答案：① 基准测试（Benchmark）：优化前后跑相同压测，记录 RT/QPS/资源，量化收益；② 监控看板：上线后持续观测关键指标，设告警；③ 自动化回归测试：核心接口性能测试纳入 CI/定时任务，一旦劣化即报警；④ 代码评审卡点：避免"为快引入坏设计"被合入；⑤ 文档记录优化点与原理，防后人误改回。本质是"测—监控—卡点"三件套。

    Q83 【进阶】【通用能力补充】用 Arthas 实战：如何不重启定位一个"接口偶发慢"的方法？火焰图怎么看？

    【Q83 追问 1】Arthas trace 对性能有影响吗？

    参考答案：有影响——trace 通过字节码增强在方法入口/出口埋点、记录每个子调用耗时，会增加方法执行开销并占用内存（尤其高频调用的方法）。生产环境应谨慎/短时使用，避免对高 QPS 核心接口长期开启；建议采样（--limit/--skipJDKMethod 过滤）、用完即停，或用 watch/monitor 替代部分场景，必要时在预发/低峰排查。

    【Q83 追问 2】火焰图（Flame Graph）里"平顶山"代表什么？

    参考答案：火焰图横轴是栈帧、宽度代表该函数在采样中占用 CPU 的比例。"平顶山"指某函数占据最宽、且顶部没有更深调用（平顶）——说明 CPU 时间耗在这个函数自身（而非它的子调用），通常是CPU 密集型热点（如大循环、正则、序列化、加密）。与之相对，"尖塔"说明瓶颈在更深层的某个子调用。定位平顶函数即定位 CPU 热点。

    【Q84 追问 1】如何区分是"DB 慢"还是"连接池不够"？

    参考答案：两者都表现为 RT 高，但根因不同：① DB 慢——拿到连接后 SQL 执行耗时长（看慢查询日志、SQL 执行耗时）；② 连接池不够——任务在等待获取连接（等待耗时占比高，拿到后 SQL 本身很快）。排查：监控连接池"等待获取连接的次数/时间"；用 trace 区分"获取连接耗时" vs "SQL 执行耗时"；show processlist 看是否有大量 Sleep/等待锁的连接。对症：DB 慢就优化 SQL，池不够就扩池或降并发。

    【Q85 追问 1】互斥锁重建缓存时大量线程阻塞怎么办？

    参考答案：热点 key 失效瞬间，大量请求争抢"重建锁"，未抢到的线程阻塞等待，可能把线程池打满。优化：① 双重检查——抢到锁的重建，未抢到的先短暂自旋/等一下再读（可能已被重建好），减少集中阻塞；② 用逻辑过期 + 异步重建（不设物理 TTL，值里带过期时间，发现过期由单线程异步刷新，其他请求先返回旧值）；③ 锁粒度细（按 key）、锁超时短；④ 预热 + 随机过期避免同时失效。

    【Q85 追问 2】如何预热缓存（大促前）？

    参考答案：① 上线/大促前批量加载热点数据到 Redis（脚本遍历热点 key 主动 set）；② 用历史访问日志识别 Top 热点，预热进缓存；③ 结合逻辑过期/永不过期 + 异步刷新让热点永不被打挂；④ 灰度放量时逐步加热；⑤ 预热失败要有告警与兜底（DB 能扛住初始流量）。核心是"别等流量来了才建缓存，提前把热点铺好"。

    Q86 【进阶】【通用能力补充】一个服务频繁 Full GC 甚至 OOM，你如何一步步定位是"内存泄漏"还是"配置过小"？

    参考答案（参考框架）：① 看 GC 日志：若 Full GC 后老年代能回落→ 多半是堆配小/流量大；若不回落且每次更涨→ 泄漏（对象被 GC Roots 长期引用）；② jmap -histo:live 看 TOP 对象；③ 导出 hprof 用 MAT 找"泄漏根"（如静态 Map 缓存无上限、ThreadLocal 未 remove、监听器未注销）；④ 修复后压测验证。泄漏典型：无限增长的缓存/集合、未关闭的资源。

    核心考察点：GC 问题根因区分（济南高级岗）。

    深入追问（完整问答）：

    【Q86 追问 1】用什么 MAT 功能找内存泄漏？

    参考答案：① Dominator Tree（支配树）——看哪些对象"支配"了大量内存，快速定位大对象持有者；② Path to GC Roots——从对象反查到 GC Roots 的引用链，找到"谁在死死抱着它不放"（如静态 Map、ThreadLocal、未关资源）；③ Histogram——按类看实例数/浅堆，发现异常多的对象；④ Leak Suspects 报告——MAT 自动给出疑似泄漏点。组合使用定位"泄漏根因对象 + 引用来源"。

    【Q86 追问 2】jmap 在容器里可能 OOM 自己，怎么避免？

    参考答案：jmap -dump 要遍历堆、本身也吃内存，容器内存受限时可能把自己或容器搞 OOM。规避：① 用 jcmd <pid> GC.heap_dump（相对更轻、现代推荐）；② 或 jmap -dump:live（只导活对象，但触发 Full GC）；③ 在宿主机/临时大内存环境执行；④ 限制堆转储频率、导出到挂盘而非容器内部；⑤ 优先用 -XX:+HeapDumpOnOutOfMemoryError 自动在 OOM 时 dump（不用人为 jmap）。

    参考答案：预扣 Redis 库存成功、异步落库失败会"Redis 已扣、DB 没单"，造成库存虚减。兜底：① 对账——定时比对 Redis 预扣记录与 DB 订单，差异回补；② 回滚消息——落库失败发"库存回补"消息（或本地消息表），消费端把 Redis 库存 +1；③ 支付超时未付自动回补（呼应 Q25）；④ 极端用"Redis 库存定期与 DB 实际占用重新校准"。核心：预扣不是终态，要有"失败/超时回补"闭环。

    【Q91 追问 2】如何防止"库存扣了但订单没生成"的一致性问题？

    参考答案：这是"扣库存与建订单"的原子性问题。方案：① 先建订单（初始状态）再扣库存，订单是事实、库存是衍生，避免"库存扣了订单没了"；② 用本地事务 + 消息：订单库落库与"库存扣减消息"原子（本地消息表/事务消息），消费端扣 Redis 库存，失败重试；③ 订单超时未支付则回补库存；④ 用状态机保证"只有支付成功才真正占用库存"。本质是"以订单为准、库存最终一致、超时回补"。

    Q92 【进阶】【简历依据：Gateway + 跨系统免登录】多端（Web/App/小程序/公众号）统一鉴权与网关设计，如何兼顾安全与性能？

    参考答案（参考框架）：① 网关（Gateway，简历已用）统一做 JWT 校验、限流、灰度；② 认证服务签发短时效 token + 刷新 token；③ 多端共享认证（SSO/免登录跳转，简历提及），用中心会话（Redis）或 JWT 无状态；④ 安全：HTTPS、验签、防重放（nonce+timestamp）、敏感操作二次校验；⑤ 性能：网关异步非阻塞、token 本地校验不查库、热点接口本地缓存鉴权结果。权衡：无状态 JWT 易扩展但难吊销，中心会话可控但有查询开销。

    核心考察点：鉴权架构整合（直接对应简历 Gateway + 免登录实践）。

    深入追问（完整问答）：

    【Q92 追问 1】JWT 如何支持"单点登出/封禁用户"？

    参考答案：JWT 自身无状态、难吊销，常见做法：① 短 access_token + 刷新 token——封禁时让 refresh_token 失效，access_token 到期自然失效（短时效降低风险）；② 黑名单/吊销列表——服务端（Redis）存"已注销 jti/用户ID+过期时间"，网关校验时查黑名单，命中即拒（牺牲一点无状态）；③ 版本号/盐——用户改密/登出时更新"token 版本"，旧 token 因版本不符失效。结合使用兼顾体验与安全。

    【Q92 追问 2】网关鉴权失败的统一响应与监控怎么做？

    参考答案：① 网关 GlobalFilter 校验失败统一返回结构化错误（如 {"code":401,"msg":"未登录/无权限"}），不泄露细节；② 记录鉴权失败日志 + traceId，便于排查与审计；③ 监控鉴权失败率/Top IP/Top 用户，异常飙升（如暴力撞库、token 批量失效）告警；④ 失败可结合限流（频繁失败 IP 限流）；⑤ 敏感操作二次校验。把"鉴权"做成可观测、可防御的一环，而非仅拦截。
